# FE-4 Performance / Scalability Audit — ddd-graphql-fe

**Correction to task framing**: this is **Astro + Solid.js** (`@astrojs/solid-js`, `solid-js: 1.9`), not React — there is no `react`/`react-dom` dependency anywhere in `package.json` and no `from 'react'` import anywhere in `src/`. All findings below use Solid's equivalents (`client:load`/`client:visible`/`client:only` islands, `createResource`/`createEffect`) since the same Astro-level hydration and data-fetching questions apply identically regardless of the UI framework.

## Summary

- **Most consequential finding**: the SSR-side urql GraphQL client (`GraphQL._client` in `src/core/api/graphql.ts`) is a process-lifetime singleton using `requestPolicy: 'cache-first'` with no TTL. The only code path that ever invalidates it (`GraphQL.resetClient()`) runs exclusively in the browser (admin/agency/tenant SPA islands, all `client:only`). Since CMS content edits are made through those browser-side mutations, **the Node/Vercel SSR process that renders public pages has no way to ever learn its cache is stale** — once a page is first rendered by a given server process, published content edits may not reappear on the public site until that process restarts/recycles.
- The public-page resolver `resolveCmsPageProps.ts` performs a **sequential (non-parallel) SSR waterfall**: `pageResolver` → `getNodesByPage` → a `for`-loop of `await fetchRepeatEntries(...)` per single-entry node → `getOneContentType` → `getPageTranslations`. The `for`-loop and the final translations call are not actually dependent on each other and could run in parallel (the sibling client-side code, `NodeChildrenList` in `NodeRenderer.tsx`, already does this correctly with `Promise.all`).
- **GSAP (+ScrollTrigger) is statically imported** at the top of `useNodeAnimation.ts` → pulled unconditionally into `FrameNode.tsx` and `ImageNode.tsx`, the two most universally-used CMS node primitives (Frame is the only container node type in the whole node-tree system). This means gsap ships in the client bundle for effectively every public page, whether or not that page's nodes have any animation configured.
- **No Astro image optimization is used anywhere** in the actual render path: `AstroImage.astro` (which wraps `astro:assets`' `Image`) has **zero call sites** in `src/` — dead code. Every CMS node that renders an image (`ImageNode.tsx`, `ContentDetailNode.tsx`, `CardListNode.tsx`) emits a plain `<img src=... loading="lazy">` with no `width`/`height`, no `srcset`/`sizes`, and no format conversion — full-resolution originals are served to every device.
- **No HTTP caching / ISR configured anywhere**: no `Cache-Control`/`s-maxage` headers set in `astro.config.mjs`, the Vercel adapter config, or `middleware.ts`, despite most public CMS pages being non-personalized and cacheable at a CDN edge. Combined with the waterfall above, every single page view re-runs the full sequential GraphQL chain server-side.
- Hydration directives are, on the whole, used correctly: `SiteFooter` and `ResponsiveNodeTree` (the actual page content) are `client:visible`; only `SiteHeader` is `client:load`, which is defensible (above-the-fold, immediately interactive nav). The public-facing customer auth pages (`dang-nhap`, `dang-ky`, `quen-mat-khau`, `dat-lai-mat-khau`, `reset-password`) are forced to `client:only` as a workaround for a `ToastProvider` SSR crash (reads `window`/`screen` outside `onMount`) — this ships zero server-rendered HTML for those pages (blank page until JS loads), though they are all `noindex: true` so the SEO cost is at least deliberate.
- Client-side sibling data-fetching (`NodeChildrenList`'s `createResource` for repeated child nodes) is done correctly with `Promise.all` — a good pattern that the server-side resolver above does not mirror.
- The urql `cacheExchange` used is the default *document* cache (query+variables keyed), not normalized — this is a reasonable choice for this workload, but note it means a mutation's blanket `GraphQL.resetClient()` (called on **every** successful mutation, anywhere in the app) discards the *entire* cache rather than invalidating just the affected entities, causing avoidable full cache-stampedes for unrelated data on every save/create/delete.
- i18n dictionaries (`vi.ts`/`en.ts`, 55 lines each) are both always loaded eagerly regardless of active locale — a non-issue at current size, but the pattern doesn't scale if dictionaries grow.
- `exceljs` and `html2canvas` are declared as dependencies but have zero import sites anywhere in `src/` — dead weight in `node_modules`/lockfile, not a runtime bundle cost (not a performance finding per se, noted only because it surfaced during the dependency scan).

## Findings

### 1. SSR GraphQL cache has no invalidation path reachable from the server — public content can go permanently stale per server process
**File**: `src/core/api/graphql.ts:140-152` (`static _client`, `getClient()`, `resetClient()`), cross-referenced with `src/shared/contexts/auth/AuthProvider.tsx:61,67`, `src/core/api/createData.tsx:132`, `src/core/components/control/Select.tsx:335` (the only 3 call sites of `resetClient()`, all client-only/browser code), and `src/modules/cms/api/resolveCmsPageProps.ts` (the SSR entry point, which never resets the client).
**Severity**: Critical
**Problem**: `GraphQL._client` is a `static` class field, instantiated lazily once and reused for the process's lifetime (`getClient()` only creates it `if (!GraphQL._client)`). `defaultContext.requestPolicy` is `'cache-first'` (also mirrored as the default in `BaseService.defaultContext`, `src/core/services/base.service.ts:34-36`). The only place that clears this cache is `GraphQL.resetClient()`, invoked from: (a) inside `GraphQL.mutation()` itself, (b) `AuthProvider`'s login/logout flows, (c) `createData.tsx`'s `refresh()`, (d) `Select.tsx`. All of these run in the **browser**, inside `client:only` admin/agency/tenant/merchant SPA islands — they execute in a completely different JS realm (the visitor's browser) than the Node/Vercel server process that runs `resolveCmsPageProps.ts` during SSR of public pages. There is no middleware, per-request client construction, or any other mechanism in `src/middleware.ts` or elsewhere that resets/bypasses this cache for the SSR path.
**Impact**: On a long-lived server process (the `@astrojs/node` standalone adapter this repo ships, `astro.config.mjs:28`, runs a real persistent Node HTTP server — not a per-request runtime), once a public page's GraphQL queries (page resolve, node tree, entries) are served once, they are cached indefinitely with no TTL. An admin publishing a content edit through the admin SPA never touches this server-side cache. The public site will keep serving the pre-edit version of that page until the process is restarted/redeployed. At scale this gets worse, not better: more traffic means the cache warms faster and more pages/paths accumulate in it, and more editorial activity means a larger and larger gap between "published" and "actually visible" content, with no operator-visible signal that anything is wrong (no errors — just silently stale HTML).
**Suggested direction**: For SSR, either disable the urql-level cache entirely (`requestPolicy: 'network-only'` or a short-request-scoped client) and rely on an HTTP/CDN caching layer instead (see finding 5), or add an explicit invalidation mechanism the backend can trigger (webhook/cache-tag purge) that's reachable from the server process. At minimum, add a bounded TTL so staleness is capped rather than unbounded.

### 2. `resolveCmsPageProps.ts` runs a sequential, non-parallel SSR waterfall on every public page request
**File**: `src/modules/cms/api/resolveCmsPageProps.ts:79-169`
**Severity**: Important
**Problem**: The function performs, per request:
1. `await PageService.pageResolver(...)` (line 81/82)
2. `await NodeService.getNodesByPage(...)` (line 88, genuinely depends on #1's `page.id`)
3. A `for (const node of singleEntryNodes) { await fetchRepeatEntries(...) }` loop (lines 113-117) — each iteration is a **separate awaited GraphQL round trip issued one at a time**, even though the iterations are independent of each other (same shape of work `NodeChildrenList` in `NodeRenderer.tsx:232-254` already parallelizes with `Promise.all`).
4. `await ContentTypeService.getOneContentType(...)` (line 130, genuinely depends on `pageEntry.contentTypeId` from #3)
5. `await PageService.getPageTranslations(...)` (line 166) — this depends only on `resolved.page.translationGroupId`, available right after step #1, but is issued dead last, after steps #2-#4 have already completed sequentially, instead of being kicked off in parallel with them.
**Impact**: Every public page view pays for N+3 to N+4 sequential network round trips to the GraphQL backend (N = number of `cardinality:'one'` nodes on the page, typically 1 but can be more), where at least the loop (step 3) and the translations call (step 5) could be parallelized with no code restructuring beyond `Promise.all`. At low traffic this just adds latency per request; at higher traffic/backend load it multiplies backend round-trip count and increases TTFB proportionally to page complexity — pages with more single-entry-bound nodes (richer editorial layouts) get proportionally slower, and there's no caching layer (finding 5) to absorb the repeated cost across visitors.
**Suggested direction**: Wrap the `for` loop in `Promise.all(singleEntryNodes.map(node => fetchRepeatEntries(...)))` the same way `NodeChildrenList` already does. Hoist `getPageTranslations` to start immediately after step #1 (in parallel with steps #2-#4), and `await` it only where the return value is assembled at the end.

### 3. GSAP + ScrollTrigger statically imported into the two most universally-used node primitives
**File**: `src/modules/cms/node/useNodeAnimation.ts:14` (`import { applyAnimationTimeline } from './applyAnimationTimeline'`) → `src/modules/cms/node/applyAnimationTimeline.ts:20-21` (`import { gsap } from 'gsap'; import { ScrollTrigger } from 'gsap/ScrollTrigger';`) → imported at module top-level by `src/modules/cms/node/primitives/FrameNode.tsx:10` and `src/modules/cms/node/primitives/ImageNode.tsx:8` (both `import { nodeAnimation } from '../useNodeAnimation'; void nodeAnimation;` — the `void` is only there to force-keep the Solid custom-directive registration side effect, but it also forces the static import chain to be evaluated).
**Severity**: Important
**Problem**: `gsap` (and its `ScrollTrigger` plugin) is a non-trivial dependency, and it is loaded unconditionally as part of the module graph for `FrameNode`/`ImageNode` — there is no dynamic `import('gsap')` gate on "does this specific node actually have an `animationRef` configured". Per project memory notes, `FRAME` is the *only* container-capable node type in the whole node-tree system, meaning nearly every CMS page tree is built out of Frame nodes, and Image nodes are equally ubiquitous for any content with pictures.
**Impact**: gsap ships in the client JS bundle for the `ResponsiveNodeTree`/`NodeRenderer` chunk hydrated on essentially every public page (`client:visible`, `CmsPageShell.astro:226`), even for pages where no node actually uses an animation timeline. This directly inflates the JS payload every visitor downloads/parses/executes on first visit to any content page, and the cost scales with total traffic (more page loads = more wasted downloads of unused animation code) rather than with how many pages actually use animation.
**Suggested direction**: Make the gsap import conditional/dynamic — e.g. have `nodeAnimation` (`useNodeAnimation.ts`) lazily `await import('./applyAnimationTimeline')` only inside `onMount`, and only when `value()` (the node's `animationRef`) is actually non-null, so pages/nodes with no animation never pull gsap into their bundle at all.

### 4. No Astro image optimization used anywhere in the actual render path; `AstroImage.astro` is dead code
**Files**: `src/core/components/astro/AstroImage.astro` (0 references anywhere in `src/`, confirmed via repo-wide search); `src/modules/cms/node/primitives/ImageNode.tsx:215`; `src/modules/cms/node/primitives/ContentDetailNode.tsx:344,412`; `src/modules/cms/node/primitives/CardListNode.tsx:67,106,145`
**Severity**: Important
**Problem**: The codebase has a component wrapping Astro's built-in `astro:assets` `Image` (`AstroImage.astro`), but it is never used — every actual CMS image render path (`ImageNode.tsx`'s `<img use:nodeAnimation=... src={src()} alt={alt()} loading="lazy" style={imgStyle()} />`, plus the hero/gallery `<img>`s in `ContentDetailNode.tsx` and the card `<img>`s in `CardListNode.tsx`) renders a plain `<img>` tag with a raw media URL. `loading="lazy"` is present (good), but there are no `width`/`height` attributes (sizing is CSS-only, and only applied when `hasDefinedSize()` is true — otherwise the `<img>` has no explicit dimensions at all), and no `srcset`/`sizes` for responsive variants.
**Impact**: (a) No layout-shift protection for the common case of a node with no explicit size — the browser can't reserve image space before the network response arrives, risking CLS. (b) Every device downloads the same full-resolution source image regardless of viewport size (a phone downloads the same bytes as a 4K desktop). (c) No automatic AVIF/WebP conversion — heavier original formats (JPEG/PNG straight from the media library) are shipped as-is. All three compound directly with content/traffic scale: more images per page and more visitors on constrained connections/devices pay the same unnecessary full-resolution download cost.
**Suggested direction**: Either wire actual CMS-uploaded images through `astro:assets` (remote image support, `image.domains`/`image.remotePatterns` in `astro.config.mjs`) to get automatic responsive `srcset`/format conversion, or at minimum have the backend/media pipeline emit `width`/`height` metadata that `ImageNode.tsx` can set as real `<img>` attributes (not just CSS), and generate a couple of pre-sized variants for `srcset`.

### 5. No CDN/HTTP caching or ISR configured despite non-personalized public content and a Vercel adapter available
**Files**: `astro.config.mjs` (Vercel adapter block, lines 21-29 — no `isr`/`imageService`/cache config passed to `vercel()`); `src/middleware.ts` (sets `X-Robots-Tag` only, never touches `Cache-Control`); repo-wide search for `Cache-Control`/`s-maxage`/`isr` found no matches in `src/`.
**Severity**: Important
**Problem**: The app supports deploying on Vercel (`@astrojs/vercel` adapter is present and auto-selected via `process.env.VERCEL`), which has first-class support for both `Cache-Control`/`s-maxage` response headers and Vercel's ISR mode — neither is configured. Public CMS pages (the entire `[...path].astro`/`index.astro` surface) are largely non-personalized (no `Authorization` header influences their content in the common case), making them good CDN-cache candidates, yet every request re-runs the full SSR pipeline including the sequential waterfall from finding 2.
**Impact**: At scale, every page view — including repeat views of the same unchanged page by different visitors — pays the full server-side render + GraphQL round-trip cost with no edge/CDN absorption. This directly multiplies backend load and TTFB with traffic volume, in a way a caching layer would otherwise flatten.
**Suggested direction**: Set `Cache-Control: public, s-maxage=..., stale-while-revalidate=...` from `[...path].astro`/`middleware.ts` for non-personalized routes, or adopt Vercel's ISR adapter option, sized to the desired content-freshness window (which also somewhat compensates for finding 1's lack of invalidation, by bounding staleness through a known TTL instead of "until process restart").

### 6. Mutation success wipes the *entire* GraphQL cache, not just affected data
**File**: `src/core/api/graphql.ts:194-204` (`GraphQL.mutation`, "Sau khi mutation thành công, thường data thay đổi -> Reset client để clear cache" → `GraphQL.resetClient()`)
**Severity**: Minor
**Problem**: Every successful mutation anywhere in the app — from any admin/agency/tenant/merchant/customer flow — discards the whole urql client (and therefore its whole document cache) rather than invalidating only the entities/queries the mutation actually affected.
**Impact**: Within a single browser session (this runs client-side, so it's scoped per visitor/tab, not shared across users — see finding 1 for the separate server-side instance), any save/create/delete anywhere in a long admin session forces every other open list/dropdown/lookup on that page to refetch from scratch on next read, even ones with no relation to what was just mutated. This is a UX/perceived-latency cost (extra network calls right after routine saves) that grows with how data-dense the admin screens are, though it is bounded to one browser session at a time so it does not compound with visitor traffic the way findings 1/2/5 do.
**Suggested direction**: Not urgent given urql's non-normalized document cache makes precise invalidation harder without more infrastructure (e.g. cache-exchange with per-type invalidation, or switching to `@urql/exchange-graphcache`); flagging for awareness rather than recommending an immediate change.

### 7. Public customer auth pages are forced to `client:only`, shipping zero SSR HTML
**Files**: `src/pages/dang-nhap.astro:6-10,32`, `src/pages/dang-ky.astro:3-4,24`, `src/pages/quen-mat-khau.astro:7,21`, `src/pages/dat-lai-mat-khau.astro:12,26`, `src/pages/reset-password.astro:8,24-25`
**Severity**: Minor
**Problem**: Each file's own comments document the root cause: `LoginForm`/`ForgotPasswordForm`/`ResetPasswordForm` wrap a `<ToastProvider>` that reads `window`/`screen` outside `onMount`, which throws during Node SSR and truncates the response — `client:only="solid-js"` was adopted as the workaround, skipping SSR for these components entirely.
**Impact**: Visitors to these specific pages get a blank page (just the static shell) until the JS bundle for the island downloads, parses, and hydrates, before any interactive form appears — a strictly worse first-paint/LCP than SSR+hydrate would give. The team has already scoped this consciously (`seo: { noindex: true, nofollow: true }` is set on every one of these pages), so the SEO cost is deliberate, but the real-visitor performance cost (a real person landing on `/dang-nhap`) is not addressed, just worked around.
**Suggested direction**: Fix `ToastProvider` to defer its `window`/`screen` reads into `onMount` (or guard with `typeof window !== 'undefined'`), which would let these pages go back to `client:load` and get real SSR content instead of a blank-until-hydrated shell.

### 8. i18n dictionaries always loaded eagerly regardless of active locale
**Files**: `src/shared/i18n/t.ts:8-9` (`import { vi } from './dictionaries/vi'; import { en } from './dictionaries/en';`), `src/shared/i18n/dictionaries/vi.ts` (55 lines), `src/shared/i18n/dictionaries/en.ts` (55 lines)
**Severity**: Minor
**Problem**: `t.ts` statically imports both locale dictionaries and keeps them both in memory (`DICTIONARIES = { vi, en }`), rather than loading only the active locale's dictionary per request/session.
**Impact**: At the current size (55 lines / 2 locales) this costs essentially nothing — flagged only because it's a pattern that stops scaling the moment more locales or a much larger dictionary are added (each additional locale's full dictionary would ship to every client/every SSR render regardless of which locale is actually active).
**Suggested direction**: No action needed at current scale; if the dictionary grows substantially or more locales are added, switch to loading only the active locale (e.g. per-request dynamic import keyed by `getLocale()`).
