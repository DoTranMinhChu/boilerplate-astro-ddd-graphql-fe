## 1. Project overview

This is a multi-tenant, DDD-flavored, GraphQL-first CMS/no-code platform, split across two independently-versioned repos that share one deployment topology:

- **`ddd-graphql-be`** — hand-rolled Express + Apollo Server backend (no NestJS), code-first custom GraphQL decorators, TypeORM + PostgreSQL, layered `domain/application/infrastructure` per module. Started life as a generic multi-tenant boilerplate (`Agency → Tenant → TenantAccount`, `Admin`, `Merchant` SSO, `Customer`) and has since had a full CMS/page-building/no-code layer built on top (`page`, `node`, `contentType`, `contentEntry`, `taxonomy`, `menu`, `form`, `headerPreset`, `footerPreset`, `siteSettings`).
- **`ddd-graphql-fe`** — Astro 6 + SolidJS islands frontend, urql for GraphQL with hand-written manual client calls (no generated hooks), Tailwind v4. Mirrors the BE's identity modules for admin portals and adds the public-facing CMS rendering layer (`src/modules/cms`).

**Topology / ports (dev)**:

| | BE (`ddd-graphql-be`) | FE (`ddd-graphql-fe`) |
|---|---|---|
| Dev command | `npm run dev` (nodemon+ts-node, `src/server.ts`) | `npm run dev` (`astro dev`) |
| Default port | `3000` (`PORT`) | `4321` (`PORT`) |
| GraphQL endpoint | `http://localhost:3000/graphql` (`GRAPHQL_PATH`) | consumed via `BACKEND_URL=http://localhost:3000` |
| DB | PostgreSQL (`DB_HOST/PORT/USERNAME/PASSWORD/DATABASE`, required, fail-fast if missing) | — |
| Cache | Redis, optional (`REDIS_HOST`; no-op/in-memory if unset) | — |
| File storage | S3-compatible via `S3_URL` (full URL w/ embedded creds) + `CDN_DOMAIN` | consumes CDN URLs returned by BE |
| Auth | JWT (`JWT_SECRET`, `JWT_EXPIRES_IN=7d`), no insecure defaults | reads token via injected resolver into urql headers |

Four FE portals share one SolidJS SPA shell, split by URL prefix: `/admin`, `/agency`, `/tenant`, `/merchant`, all wrapped by `src/layouts/dashboard`; the public marketing/CMS site is server-rendered by Astro at the root. `src/modules/customer` auth screens are separate public Solid islands (not part of the admin SPA).

Both repos' root `README.md` describe an earlier, more minimal "generic boilerplate, domain modules stripped" state — this predates the CMS/no-code build-out documented here and is **stale**; treat this file, not those READMEs, as current (see §7).

## 2. Tech stack & conventions

### Backend (`ddd-graphql-be`)

- **Server wiring** — `src/server.ts` (single `Server` class): Express + Helmet + CORS (`CORS_ORIGINS` allowlist, reflects any origin with a warning if unset — required in prod) + `express-rate-limit` (global, `RATE_LIMIT_WINDOW_MS`/`RATE_LIMIT_MAX_REQUESTS`, default 15min/10000, skips `OPTIONS`/`/health`) + per-request timeout (`REQUEST_TIMEOUT_MS`, 503 on expiry) + Apollo Server (`@apollo/server` + `@as-integrations/express4`) mounted at `GRAPHQL_PATH` (default `/graphql`). GraphQL introspection/landing page gated by `!IS_PROD || ENABLE_GRAPHQL_INTROSPECTION==='true'`. Query depth capped via `createDepthLimitRule(GRAPHQL_MAX_DEPTH)` (`src/core/infrastructure/http/graphqlDepthLimit.ts`, default 15). Health checks: `/health` (liveness) and `/health/ready` (checks DB + Redis if configured). `src/cluster.ts` is an alternate entrypoint using Node `cluster` (`WEB_CONCURRENCY` workers).
- **Custom GraphQL decorators** — all in `src/core/shared/decorators/graphQL.decorators.ts` + `graphQLPermission.decorator.ts`: `@ObjectType(name?)`, `@InputType(name?)`, `@Field(options?)` (auto-thunks class refs to dodge circular imports), `@Resolver(of?)`, `@Query(name?, options?)`, `@Mutation(...)`, `@Subscription(...)` (declared, not wired by the loader), `@FieldResolver(options?)`, `@Args(name?, options?)`, `@Context()`/`@Parent()`/`@GQLInfo()`/`@GQLLoader()`/`@GQLCurrentUser()`/`@GQLQuery()` (param injectors), `@GQLAuthorized(required?)`, `@GQLPublic()` / `@GQLOptionalAuth()` (alias), `@GQLCache(options?)`, `RegisterEnum(enumObj, name)` (function, registers TS enums into the schema), and `@GQLPermission(config)` (fine-grained permission, see §6).
- **Schema loader / auto-registration** — `src/core/infrastructure/http/graphQLSchema.loader.ts` (`GraphQLSchemaLoader` singleton): globs `src/modules/**/infrastructure/http/graphql/*.resolver.{ts,js}`, filters through `isModuleFileAllowed` (multi-instance denylist, see below), dynamically `import()`s each, checks `GRAPHQL_RESOLVER` metadata, instantiates and registers Query/Mutation/FieldResolver entries. `mapToGraphQLType` recursively resolves JS types/thunks/enums into `graphql-js` types, falling back to `GraphQLMixed` when unresolvable. REST controllers follow an identical glob pattern via `restRouter.loader.ts` (`*.controller.ts` files, `@RestController`/`@Get`/`@Post`/... decorators, same service layer).
- **`GraphQLMixed` scalar** (`src/core/shared/graphql/scalars.ts`) — a passthrough `GraphQLScalarType` (`serialize`/`parseValue` are identity, `parseLiteral` uses `valueFromASTUntyped`) used as the escape hatch whenever the schema loader can't resolve a concrete type — i.e. the workaround for typing JSONB columns (`style`, `props`, `data`, `dataBinding`, etc.) and dynamic filter/pagination inputs in GraphQL. Also exports `GraphQLDate` (Vietnam-offset `DateTime` scalar).
- **Permission system** — two layers. Coarse: `ERole` (`SUPER_ADMIN, ADMIN, AGENCY_OWNER, AGENCY_MANAGER, AGENCY_STAFF, TENANT_OWNER, TENANT_MANAGER, TENANT_STAFF`) + `ERoleScrope` (`ADMIN, MERCHANT, AGENCY, TENANT, CUSTOMER`) gate resolver access via `@GQLAuthorized([...])`/`@GQLPublic()`, checked by `RBACService.authorizeRoles`. Fine-grained: `EPermission` enum (`src/modules/permission/enums/permission.enum.ts`) + a JSONB `ScopeRule` (`ALLOW_ALL|DENY_ALL|INCLUDE|EXCLUDE|SELF|OR|AND`, `src/modules/permission/types/scope.types.ts`) stored per-`(tenantId, tenantAccountId, permission)` row in `AccountPermissionEntity`. `@GQLPermission(config)` (`src/core/shared/decorators/graphQLPermission.decorator.ts`) stores config; `applyGQLPermission()` (`src/core/infrastructure/http/graphQLPermission.handler.ts`) resolves it at call time via `accountPermissionService.resolvePermission()`, then either lets the call through (`ALLOW`), throws/empties (`DENY`), or injects a `where` filter into list args / calls the ownership-check helper `recordMatchesRule(record, rule, account)` for single-record mutations. Tenant/agency owners bypass the DB lookup entirely (`ALLOW_ALL` synthesized). `isScopeSubset()` guards against privilege escalation when one account grants permissions to another.
- **Base classes** — `ABaseRepository<T>` (`src/core/infrastructure/database/base.abstract.repository.ts`): `findAllCursorByCondition` (the shared cursor+offset pagination/filter/search DSL — `EFilterOperator` set `$eq/$ne/$gt/$gte/$lt/$lte/$in/$nin/$like/$ilike/$sw/$ew/$between/$null/$notNull`; opaque base64 cursors `[sortValue, id]`; row-value comparison for µs precision), plus `findById/findOneByCondition/create/createMany/updateById/updateByCondition/softDeleteById/restoreById/countByCondition/existsByCondition`, protected `paginateQueryBuilder()`, and safety helpers `hasColumn()`/`sanitize()` (drops unknown filter keys so a stray client filter can't 500). `BaseService<T>` (`src/core/application/services/base.service.ts`): wraps the repository, adds `eventBus.publishAsync('<entity>.created/.updated/.deleted/.restored', ...)` on every mutation, `findAllPagination()` (merges `@GQLPermission`-injected `_scopeOr` branches), and DataLoader cache invalidation (`invalidateLoaderCache`).
- **Testing** — Jest (`jest.config.js`, `preset: ts-jest`, `roots: ['<rootDir>/test']`, `testMatch: **/*.test.ts`). All test files live under a centralized top-level `test/` tree mirroring `src/`/`scripts/` (no more `__tests__/` subfolders). Convention: a `makeService(repoOverrides)` factory builds plain **literal fake objects** for the repository (e.g. `{ findOneByCondition: jest.fn(async () => null), ... }`) and constructs the real service class directly against the fake — no TypeORM, no `AppDataSource.initialize()`, no test containers, anywhere. External SDKs (`google-auth-library`, etc.) are `jest.mock()`'d. Example: `test/modules/customer/application/services/customer.service.test.ts`.
- **Database** — `src/config/database.config.ts`: `synchronize: false` hardcoded at the `DataSource` level (TypeORM auto-runs it inside `.initialize()` regardless of env if true — treated as dangerous); explicit conditional `synchronize()` call only runs if `NODE_ENV==='development'` (and `DB_SYNCHRONIZE!=='false'`) or on a fresh `INSTANCE_ROLE=NODE` bootstrap. Migrations always run first (`AppDataSource.runMigrations()`) unless `NODE_ENV==='test' && DB_SKIP_MIGRATIONS==='true'`. A Postgres advisory lock (`pg_advisory_lock(hashtext('app_schema_sync'))`) serializes schema ops across cluster workers. `src/config/instance.config.ts` ships a minimal `INSTANCE_ROLE` (`CENTRAL`|`NODE`) pattern — `NODE` instances filter out resolver/controller files whose module folder is in `AGENCY_NODE_DENYLIST_MODULES` (ships **empty** — no-op example).

### Frontend (`ddd-graphql-fe`)

- **Rendering model** — Astro 6 pages are thin shells; SolidJS islands (`client:visible`/`client:load`) do the interactive work. Admin/agency/tenant/merchant portals mount one SPA (`src/shared/common/app/App.tsx` + `AppRoutes.tsx`, SolidJS router, client-side routing after first load). The public CMS site is SSR'd per-request by Astro (`src/pages/[...path].astro`, `src/pages/index.astro`) via `resolveCmsPageProps.ts`.
- **GraphQL client** — `src/core/api/graphql.ts`, a static `GraphQL` class over `@urql/core` (`Client` with `requestPolicyExchange`, `cacheExchange`, `fetchExchange`, always POST). No generated hooks: every domain has a hand-written service file (`src/shared/services/<name>/<name>.service.ts`) extending `CrudService`/`BaseService` (`src/core/services/base.service.ts`) that builds a typed document per call via `typed-graphql-builder`'s `query()`/`mutation()`/`fragment()`/`$` helpers (imported from `src/shared/generated/typed-graphql.ts`) and calls `this.queryApi/mutationApi`. Auth header is recomputed per-request via an injected token resolver (`GraphQL.setTokenResolver`, avoids races on account switch); every request also sends `x-locale` and, for mutations, `x-acting-tenant-id` when set.
- **Generated client** (`src/shared/generated/{schema.graphql, typed-graphql.ts}`) — real generated output (not stale/empty), but generated from a small **hand-authored seed schema**, not a live backend introspection. `npm run gengraph` (`scripts/generate-graph.mjs`) is the actual, working regeneration path: introspects `BACKEND_URL`, rewrites `schema.graphql`, runs the real `typed-graphql-builder` CLI, patches output. **`npm run codegen` (`graphql-codegen`) is broken** — see §6.
- **Feature flags** — `PublicConfig` enum (`src/env.config.ts`) + `getClientConfig()`/`getServerConfig()` (`src/core/helpers/config.{client,server}.ts`). `getServerConfig` reads `process.env`/`import.meta.env` directly; `getClientConfig` reads a `window.config` object injected server-side by `src/layouts/ConfigInjector.astro` (loops every `PublicConfig` key). See §6 for the full flag list — no boolean feature flag is currently defined this way (the one that existed, `CMS_NODE_TREE_ENABLED`, was removed once Node-tree became the sole page-building system).
- **Testing** — Vitest, `.test.ts` files only, **zero** `.test.tsx`/component tests anywhere (`vitest.config.ts`; 14 test files as of this writing, e.g. `src/shared/services/merchant/merchantSwitchConfig.test.ts`, `src/modules/cms/node/{applyNodeStyle,applyNodeLayout,buildNodeTree,evaluateVisibilityRules,nodeDataBinding}.test.ts`). Pattern: pure-logic/service functions and lookup tables, `vi.mock()` for service dependencies, no DOM/SolidJS rendering assertions.
- **i18n** — hand-rolled, no i18n library. `src/shared/i18n/locale.ts`: `Locale = 'vi'|'en'`, `DEFAULT_LOCALE='vi'`, a SolidJS signal persisted to `localStorage` (`agribase:locale`), SSR-safe. `dictionaries/vi.ts` is the source of truth (`as const`), assembled from per-module dictionaries (`src/modules/<name>/<name>.i18n.ts`, e.g. `cms.i18n.ts`) plus shared namespaces (`common`, `locale`, `layoutsSharedVi`). `dictionaries/en.ts` is a `DeepPartial` mirror — missing EN keys fall back to Vietnamese. `t.ts`'s `TranslationKey` is a compile-time dotted-path union over the VI dictionary; `t(key)` resolves `dict[locale][key] ?? vi[key] ?? key`. Locale is client-persisted only — no URL/path-based locale routing on the FE i18n layer itself (the CMS content-locale system in §4 is separate and URL-prefix-based).
- **Config directory layout** — `src/core/config/` (build-tooling: `scalars.txt` scalar-type map for codegen, oxlint overrides) vs. `src/shared/config/` (singular — `tenantBusinessRole.meta.ts`, UI metadata) vs. `src/shared/configs/` (plural — `scopeFieldRegistry.ts`, permission-scope picker registry). The singular/plural split looks like accidental naming drift rather than an intentional layer — each holds one unrelated file, no functional overlap.

## 3. Domain modules — current state (BE `src/modules/*`)

Every entity below extends `BaseEntity` (`id: uuid`, `createdAt`, `updatedAt`, `deletedAt`, soft-delete) unless noted; tenant-scoped entities extend `BaseWithTenantEntity` → `BaseWithAgencyEntity` (adds `tenantId`/`tenant`, `createdByTenantAccountId`, `agencyId`/`agency`).

**Identity/tenancy hierarchy** (confirmed from code): `Agency` (top, optional) → `Tenant` (`agencyId` FK) → `TenantAccount` (`tenantId` FK, inherits `agencyId`). Login identity is decoupled from org context: `Merchant` is the one username/password identity; `TenantAccount`/`AgencyAccount` link to a `Merchant` via `merchantId` and authenticate against **the Merchant's password**, not their own (`AgencyAccountEntity.password` exists but is vestigial/unused by the login flow). `Admin` and `Customer` are independent identities, not part of this tree.

## 4. CMS page-building system in detail

This is the most complex subsystem and the one that changed most over the project's lifetime. A single page-body model — Node-tree — now covers everything; the legacy `Section` model described in earlier revisions of this document has been deleted entirely (see §4.2).

### 4.1 `page` module — the routing shell

`PageEntity` (`page/domain/entities/page.entity.ts`, table `page`): `internalName, path(unique), pageType: EPageType(default STATIC_MODULAR), templateKey?, parentPageId?, contentTypeId?, headerPresetId?, footerPresetId?, status: EPageStatus(default DRAFT), publishedAt?, scheduledAt?, locale(default 'vi'), translationGroupId(uuid, auto-generated), seo: SeoType(jsonb), style?(jsonb), seoFieldMapping?: Record<string,string>(jsonb), rootNodeId, dataBinding?(jsonb)`.

- `EPageType` = `STATIC_MODULAR | COLLECTION_LISTING | SPECIAL` — **`COLLECTION_DETAIL` was removed** (confirmed absent in code; superseded an earlier design, see §7).
- `EPageStatus` = `DRAFT | SCHEDULED | PUBLISHED | UNPUBLISHED | ARCHIVED`.
- Sibling entities: `PageVersionEntity` (`page_version`: `pageId, snapshot(jsonb), publishedBy?, label?` — no hard FK, survives page deletion) and `RedirectEntity` (`redirect`: `fromPath(unique), toPath, statusCode: 301|302`).
- Public resolvers: `pageResolver(path)`, `getSitemapUrls()`, `getPublicDetailPathByContentType`, `getPageTranslations` — all `@GQLPublic()`. Staff: `previewPageResolver` (bypasses visibility rules entirely for preview), `createPage/updatePage/deletePage` (`PAGE_CREATE/UPDATE/DELETE`), `publishPage/unpublishPage/getPageVersions/restorePageVersion` (`PAGE_PUBLISH`/`PAGE_VIEW`).
- **`pageResolver`/`previewPageResolver` fetch the page's Node tree via `NodeService` — there is no other rendering path.** `PageResolverResultType` has a `nodes: NodeEntity[]` field (no `sections` field — the type was removed with the `section` module). `createPage()` transactionally creates the page's root `Node` in the same call, so `rootNodeId` is always set — there is no "page exists but has no root node" state.
- `publish()` snapshots `{page, nodes}` into `PageVersionEntity`, and `restorePageVersion` recreates the full Node tree from that snapshot — Node-tree data (including responsive overrides, animation timelines, visibility rules) round-trips fully through Version History.
- Business rules: `path` globally unique + validated (`slug.util.ts`); `assertPathNotLocaleShadow` blocks a page's first path segment from colliding with an enabled locale code unless it's that page's own locale; `createTranslation` clones a Page+Node-tree into a new locale under the same `translationGroupId`; `findByParamPattern`/`findDetailBinding` are the two URL-matching strategies that replaced `COLLECTION_DETAIL` (the latter reads `Page.dataBinding` — see §4.2).

### 4.2 `node` module — the sole page-building model

The legacy `Section` module (flat, 22 fixed block types, no free canvas) was deleted entirely by the CMS visual-builder roadmap's Phase 0 — the `section` DB table, `ddd-graphql-be/src/modules/section/**`, and every FE Section-builder file (`PageBuilder.page.tsx`, `SectionRenderer.tsx`, `sectionRegistry.ts`, etc.) no longer exist. Node-tree, described below, is the only page-building system.

Table name is **`page_node`** (deliberately not `node`, to avoid tooling ambiguity), GraphQL type/TS class stay `Node`/`NodeEntity`. Exact entity fields (`node/domain/entities/node.entity.ts`):

```
pageId: string                      // @Index
parentId?: string                   // @Index, nullable — null = root
order: number                       // default 0
type: string                        // free string, resolved via FE nodeTypeRegistry — no DB enum
layoutMode: 'flow' | 'free'         // plain string column, default 'flow' — governs how CHILDREN are laid out, not the node itself
style: Record<string, any>          // jsonb, default {}
layout: Record<string, any>         // jsonb, default {} — shape depends on PARENT's layoutMode
props: Record<string, any>          // jsonb, default {}
dataBinding: Record<string, any>    // jsonb, default { mode: 'static' } — { mode: 'static'|'boundField', field? }
repeat?: Record<string, any>        // jsonb, nullable — { source: 'own'|'related'|'backlink'|'mixed', mode?, contentTypeKey?, filter?: GenericDataSourceFilter[], entryIds?, taxonomyFilter?, sort?, limit?, matchField?, sourceContentTypeId?, sources? }
visibilityRules?: Record<string, any> // jsonb, nullable — { logic: 'AND'|'OR', conditions: [...] } — conditions: device|authState|dateRange|fieldValue|queryParam
responsiveOverrides: Record<string, any> // jsonb, default {} — { tablet?: {style?,layout?}, mobile?: {style?,layout?} } — ACTIVE, read by applyNodeStyle/applyNodeLayout (desktop-first cascade)
animationRef?: Record<string, any>  // jsonb, nullable — an AnimationTimeline object ({ keyframes: AnimationKeyframe[], trigger: 'onLoad'|'onScroll', scrollStart?, repeat?, mobileEnabled? }) for the 8 hand-authorable primitives ONLY (see below)
```

`layout` shape by parent `layoutMode`: **flow** → `{direction,wrap,justify,align,gap,display,gridTemplate}` (container) / `{order,grow,shrink,basis,alignSelf,gridColumn,gridRow}` (child); **free** → `{x,y,width,height,rotation,zIndex,constraints:{horizontal,vertical}}` (fully editable through the builder UI, see below).

- **Self-referencing tree** via `parentId` — no DB FK/cascade; all invariants enforced in `node.service.ts`: `MAX_TREE_DEPTH=30`, `MAX_NODES_PER_PAGE=500`, `assertNoCycle()` (walks parent chain, capped), `assertDepthAllowed()` (accounts for moved-subtree height), `assertValidParent()` (same-page only), `assertCountAllowed()`. `createNode`'s order-assignment uses a `pessimistic_write` row lock on the parent to avoid concurrent-insert races. BE performs **zero type validation** — any string is a valid `type`; a container-type check (only `FRAME` may have children) is FE-enforced only, by design (adding a new node type never requires a DB migration).
- Resolvers: `getNodesByPage(pageId)` (public) plus staff `createNode/updateNode/deleteNode/moveNode/duplicateNode/reorderNodes` (all `NODE_MANAGE`).
- `PageEntity.rootNodeId` is the only structural link to Page — always set (`createPage()` creates the root Node transactionally).
- **No feature flag gates Node-tree rendering** — the `CMS_NODE_TREE_ENABLED` flag that once gated this (default off, additive alongside Section) was removed along with Section; Node-tree is unconditionally the render path for every page.

**Renderer** (`NodeRenderer.tsx`, `src/modules/cms/node/`): recursive — evaluates `visibilityRules` (`evaluateVisibilityRules.ts`, AND/OR over `device|authState|dateRange|fieldValue|queryParam` conditions; `device` is a reactive `Breakpoint` accessor, real on both the public site (`useBreakpoint()`, real `window.innerWidth`) and the admin canvas (manual preview switcher — see below)), resolves the component + field-schema via `nodeTypeRegistry[node.type]`, computes CSS via `applyChildLayout`/`applyContainerLayout` (`applyNodeLayout.ts`) and `applyNodeStyle.ts` (structured `StyleObject` → flat CSS, breakpoint-cascade-aware), applies the node's `AnimationTimeline` via the `use:nodeAnimation` directive (hand-authorable primitives only), wraps in a per-node `ErrorBoundary`. `NodeChildrenList` resolves `repeat` bindings (`fetchRepeatEntries`, 4 sources: `own`/`related`/`backlink`/`mixed`, calls `ContentEntryService.*` — `repeat.taxonomyFilter` still has no BE param support, silently ignored) via `resolveRenderableChildren.ts`.

**Node families, by design:**
- **9 true hand-authorable primitives** — `Frame, Text, Image, Shape, Video, Icon, Button, FormEmbed, CustomCode` (`ENodeType`, as-const, not a DB enum) — the only types the Node Builder's palette offers for new nodes today. `FormEmbedNode.tsx` is fully self-contained (the legacy `FormSection.tsx` it once reused no longer exists). `Frame` composes with 3 `behavior` variants (`accordion-item`, `spotlight-list`, `carousel`) and a `repeat.source:'local'` mode; `Text` has `richText`/`countUp`/`spotlightReveal` capabilities; `DataBinding.mode:'mixedField'` sources one repeat entry from several different Content Types at once — together these primitives can now compose everything the 13 now-deleted `RETIRED_NODE_TYPES` used to need a dedicated component for (see the "retire specialized node types" roadmap, 2026-08-20 → 2026-08-24; full deletion of the 13 registry entries/component files happened later, in Motion System Unification's Task 2, §4.10).
- **`MIGRATION_ONLY_NODE_TYPES`** (`node.constants.ts`) — **now an empty Set.** Originally 14 types produced only by the Section→Node backfill migration with no Inspector tab of their own; all 14 were ported to real, hand-authorable Content/Style/DataBinding tabs over Canvas Editor v2 (2026-08-17) — the set stays in the codebase (and `NodePalette.tsx` still consults it) as a currently-inert extension point, not dead code.
- **`RETIRED_NODE_TYPES`** — **deleted entirely, no longer exists.** Through 2026-08-24 this was a 13-member set (`MediaHero, IntroRail, SpotlightList, StatMetrics, TimelineList, ProcessSteps, ContactColumns, AccordionList, InquiryForm, ProjectShowcase, LogoGrid, FeaturedEntry, MixedFeed`) naming 13 real, working, self-contained bespoke components kept alive only because existing pages might still contain real rows of these types, each running on the OLD preset-based GSAP animation system (`presetRegistry.ts`/`useAnimate.ts`, `props.legacyAnimation`). **Motion System Unification (Phase 5, Task 2, 2026-08-30 — see §4.10)** confirmed 0 real rows remained for all 13 (relying on the prior live DB finding, not a fresh query) and deleted the `RETIRED_NODE_TYPES` set declaration, all 13 `ENodeType` members, all 13 `nodeTypeRegistry` entries, and all 13 component files (+ their `.test.tsx` siblings) outright — this paragraph's old "kept intact until migrated" framing no longer applies to anything. `presetRegistry.ts`/`useAnimate.ts`/`AnimationLayer` themselves were separately deleted by the same plan's Task 11 (§4.10) — there is no longer a second, older animation system anywhere in this codebase for any node type to be "excluded" from. **`ContentDetail` was deliberately excluded from the original retirement set** — kept as an accepted first-class utility type alongside `Table`/`CardList`, unaffected by any of the above.

**Widget Registry v2** (`nodeRegistry.ts`): `nodeTypeRegistry: Record<string, NodeTypeDescriptor>` — one descriptor per type: `renderer`, `icon`, `labelKey`, `capabilities` (booleans: `style`/`animation`/`dataBinding`/`repeat`/`layoutChildren`), and a real **`fieldSchema: FieldDescriptor[]`** (key/label/control/default/options — control types: `text|textarea|richtext|code|image|color|select|number|boolean|url`) driving a generic `FieldRenderer` in the Inspector's Content tab (no more per-type hand-written `<Show>` branches). `nodeRegistry`/`nodeCapabilities`/`NODE_TYPE_META`/`MIGRATION_ONLY_NODE_TYPES` all survive as derived getters off this one map, for call-site compatibility.

**`ENodeType.CUSTOM_CODE`** — raw HTML/CSS/JS embed node, 3 admin-selectable isolation modes: `direct` (raw inject, no CSS isolation, full `window`/`document`/cookie access — Webflow/Framer-Embed style), `shadow` (default — Shadow DOM, 2-way CSS isolation, JS still has full page access), `sandboxed` (`<iframe sandbox="allow-scripts">`, no `allow-same-origin` — true origin-level isolation). Content is deliberately NOT passed through DOMPurify (same trust model as any other admin-editable field — sanitizing would strip the `<script>` this node exists to allow).

**Canvas Editor** (`NodeBuilder.page.tsx` + supporting modules) — full Figma/Webflow-style direct manipulation, not just a form-based tree editor:
- **Selection**: `NodeSelectionContext` — Set-based multi-select (click / Shift-range / Ctrl-toggle), independent of Undo/Redo (selection itself isn't undoable, matching Figma/Webflow convention).
- **Undo/Redo**: `CommandManager` (real command-pattern, 2 stacks) + Command factories in `nodeCommands.ts` (`createAddNodeCommand`, `createDeleteNodesCommand`, `createUpdateNodePropertyCommand`, `createMoveNodeCommand`/`createMoveNodesCommand`, `createDragNodesCommand`) covering every edit path (every Inspector tab, add/delete, move/reorder, drag/resize/rotate, single and multi-select). A wholesale node-tree replace (Version History restore, initial page load) calls `CommandManager.reset()` to avoid stale-Command staleness.
- **Layers panel** (`LayersPanel.tsx`, replaced the old button-only tree list): flattened depth-first list respecting collapse state, tree-aware drag-and-drop supporting both same-parent reorder AND reparent (before/after/inside drop zones, FRAME-only container guard — client-side only, BE never validates this).
- **Direct canvas manipulation** (free-layout children only): drag-to-reposition (single + multi-select), 8-handle resize, 1 rotate handle (Shift = 15° snap), snap-to-grid (8px, toggleable) + snap-to-sibling (4px threshold, always on), rubber-band marquee multi-select. `NodeCanvasOverlay.tsx` renders as a DOM sibling of the selected node reusing its own free-layout CSS — no manual screen-space math, correct even under nested rotation.
- **Numeric Transform tab** (`NodeTransformTab.tsx`) — x/y/width/height/rotation/z-index fields, visible when the selected node's **parent** (not itself) has `layoutMode==='free'`.
- **Responsive**: `NodeRenderContext.device` is a reactive `() => Breakpoint` accessor everywhere (public site: real `useBreakpoint()`; admin canvas: manual `previewBreakpoint` signal, a 3-button Desktop/Tablet/Mobile switcher at the top of the Inspector — resizes the canvas preview width and redirects the Style/Transform tabs to read/write `responsiveOverrides.{tablet|mobile}` instead of the base field). Cascade is desktop-first: a tablet override also applies at mobile unless mobile overrides that same field itself.
- **Animation** (6th and last Inspector tab, `NodeAnimationTab.tsx`) — an ordered keyframe-step list editor (add/remove/reorder, each step: optional free-text sub-element target, property [`opacity|x|y|scale|rotation`], from/to/duration/delay/easing, optional `stagger`) + 7 one-click quick-presets (Fade In/Up, Slide Left, Scale In, plus the 3 role-differentiated reveal presets added by Motion System Unification's Task 13 — see §4.10) + trigger (onLoad/onScroll)/scrollStart/repeat/mobileEnabled controls, gated `capabilities.animation && !MIGRATION_ONLY_NODE_TYPES.has(type)`. Built by `applyAnimationTimeline.ts` (constructs one real `gsap.timeline()`, keyframes positioned by absolute-second offsets, respects `prefers-reduced-motion` — see §4.10) + the `useNodeAnimation.ts` Solid directive, wired onto all 9 hand-authorable primitives' root elements AND (via the same `nodeAnimation`/`AnimationTimeline` mechanism) `SiteHeader.tsx`/`SiteFooter.tsx`. This is now the **only** animation system in the codebase — the older preset-based GSAP system this sentence used to describe itself as "independent of" has been deleted entirely (Motion System Unification, §4.10).
- Inspector tab order: **Transform → Content → Style → DataBinding → Visibility → Animation** (6 tabs total).

### 4.5 Theme layer & style pipeline

Built across a 19-task plan (`docs/superpowers/plans/2026-08-28-theme-layer-style-pipeline.md`), this is **Phase 1** ("Design System / Theme layer" + "rewrite Style/Render pipeline" + semantic typography) of the longer multi-phase upgrade roadmap in `feedback/UPGRADE-PROMPT.md` — see the scope-boundary note at the end of this subsection for what's still ahead.

**`ThemeEntity`** (BE, `theme/domain/entities/theme.entity.ts`, table `theme`): `name, isDefault(default false), colors: ThemeColors(jsonb), typography: ThemeTypography(jsonb), layout: ThemeLayout(jsonb), motion: ThemeMotion(jsonb)` — one row per design-token set, not per Page. `ThemeColors = { light: ThemeColorSet, dark?: ThemeColorSet }` (15 keys: background/surface/surfaceMuted/foreground/foregroundMuted/border/primary/onPrimary/secondary/onSecondary/accent/onAccent/success/warning/danger — dark mode is data-capable today but has no UI activation path, see below). `ThemeTypography` carries `displayFont`/`bodyFont`/`monoFont?` (`ThemeFontDef`: family/googleFontUrl?/fallback/weights) plus a `scale: Record<TypographyRole, {...}>` (`TypographyRole` = `display|h1|h2|h3|h4|bodyLg|body|small|caption`). `ThemeLayout`/`ThemeMotion` carry spacing/container-width/radius/shadow/border-width and duration/easing/signature tokens respectively. Staff CRUD via `ThemeResolver` (mirrors `HeaderPresetResolver` exactly: `getAllThemes`/`getOneTheme` STAFF_ROLES, `createTheme`/`updateTheme`/`deleteTheme`/`setDefaultTheme` ADMIN_ROLES); one theme is seeded by `scripts/seed-default-theme.ts` (real invocation needs `-r tsconfig-paths/register -r dotenv/config`, not the plan's literal bare `ts-node` command).

**`PageEntity.themeId?`** (nullable) selects a Page's own theme; `PageResolver.resolveTheme()` (BE) implements the same own-wins-else-default fallback chain as the pre-existing `resolveHeaderFooter()`: own `themeId` if set and resolvable, else the `isDefault` theme, else `undefined`. Wired into both `resolvePage` branches (`exactMatch`/`paramMatch`) of `pageResolver`/`previewPageResolver`.

**CSS custom-property injection**: `CmsPageShell.astro` calls `resolveThemeCssVars(theme, 'light')` (FE, `modules/theme/resolveThemeCssVars.ts`) and spreads the result (`--color-*`, `--font-display`/`-body`/`-mono`, `--container-content`/`-wide`, `--motion-*`, plus per-role `--type-<role>-min/max/line-height/weight/letter-spacing`) onto `<body style=...>`, alongside `<link rel="stylesheet">` tags for each font role's Google Fonts URL. Getting `resolved.theme` to actually reach this point needed two fixes beyond the obvious (`resolveCmsPageProps.ts`/`CmsPageShell.astro` themselves): `page.service.ts`'s GraphQL query didn't select the `theme` field, and `index.astro`/`[...path].astro` didn't pass the `theme` prop down — both are real, easy-to-miss dead ends in a prop-threading chain that this plan's Task 9 found and closed. **The admin Node Builder canvas needed the identical injection wired in separately** (`NodeBuilder.page.tsx`, found live during Task 16, not covered by the original brief): without it, `applyNodeStyle`'s `resolveColorValue()` correctly emits `var(--color-primary)` for a token-styled node, but the canvas preview has nothing to resolve that CSS variable against, so a persisted color token renders correctly on the public page yet invisibly in the editor. Both injection points currently hardcode `mode: 'light'` — no dark-mode toggle exists anywhere yet (data-capable, not activated).

**Style compiler — `applyNodeStyle.ts`**: previously purely literal-value CSS generation; now resolves `{ tokenRef: 'key' }` color values into `var(--color-<kebab-key>)` references via a `resolveColorValue()` helper, applied at every color-bearing `StyleObject` field: `typography.color.value` (solid/image/gradient/video sub-modes), `background.value` (color/gradient/image types), `border.color`. This took **four review rounds** to close fully — each round found one more raw (non-`resolveColorValue()`) read of a color-bearing field elsewhere in the render tree that would have silently produced `background-image: [object Object]` once a token ref reached it: `FrameNode.tsx`'s `videoLayer()` and `breatheLayer()`, `TextNode.tsx`'s video-fill branch, `applyNodeStyle.ts`'s own gradient/image background sub-cases. **Maintenance note for future code**: any new code that reads a color-bearing `StyleObject` field (`typography.color.value`, `background.value`, `border.color`) must route it through the exported `resolveColorValue()` in `applyNodeStyle.ts`, never read it raw — a plain string passes through unchanged, so this is always safe to do even before a token ref is possible at that call site. **(M5, final review)** two color-bearing fields were deliberately **not** widened to accept theme tokens and stay outside this rule: `shadow[].color` (`StyleObject.shadow` is a plain `{x,y,blur,spread,color,inset?}` array, `color` typed as a raw `string`) and `background.overlay` — only `typography.color.value`, `background.value` (for `type:'color'`/`'gradient'`/`'image'`), and `border.color` were widened to `string | ThemeColorTokenRef`.

**`compileNodeStateCss.ts`** (NEW file, replaced the old single-purpose `applyNodeHoverStyle.ts`): unifies `:hover`/`:focus-visible`/`:active`/`::before`/`::after` compilation for a node's `style.hover`/`.focus`/`.active`/`.before`/`.after` fields, each still rendered as a sibling `<style>` tag per node in `NodeRenderer.tsx` — the same proven SSR-safe per-node mechanism as before, **not** a page-level CSS collector. `style.hover`/`.focus`/`.active` also support an optional `reducedMotionOverride` (a same-shaped partial override): when set, the base override's properties are wrapped in `@media (prefers-reduced-motion: no-preference)` and the `reducedMotionOverride`'s own properties render as an unconditional fallback rule on the same selector. **A real, non-obvious CSS fact was found live (Task 12) and is now correctly handled**: `:hover`/`:active` propagate to ancestor selectors (hovering/pressing a child puts every ancestor into `:hover`/`:active` too), but `:focus`/`:focus-visible` do **not** — only the exact focused element matches. The compiler therefore special-cases `focus-visible`: self-scope targets the wrapper's child directly (`[data-node-id="ID"] > *:focus-visible`, since that child is the actually-focusable element), while parent-scope uses `:focus-within` on the parent (`[data-node-id="PARENT_ID"]:focus-within [data-node-id="ID"] > *`) — a **disclosed trade-off**, not a like-for-like port: there's no single CSS selector that is simultaneously ancestor-propagating and keyboard-only, so parent-scope focus loses the "keyboard-only, not just any focus" restriction that `:focus-visible` normally guarantees. `applyNodeBackgroundAnimation.ts` and `applySpotlightRevealStyle.ts` remain their own **separate, untouched** modules — explicitly deferred to a future Motion-system phase (Phase 5 of the wider roadmap) — so `compileNodeStateCss.ts` is **not** a full unification of every CSS-generating mechanism in this codebase, only hover/focus/active/before/after. `style.before`/`.after` (`PseudoElementStyle`: `content` required, plus optional `background`/`border`/`shadow`/`effects`/`transform`/`size`) compose through the same `applyNodeStyle()` call, so their color fields get token resolution automatically; a pre-existing, unrelated seam is disclosed but not reconciled — `applySpotlightRevealStyle.ts` independently compiles its own competing `::after` on the same selector shape for `props.spotlightReveal===true` nodes, so a node using both features would get two `::after` declarations. **(M4, final review — corrected)** this is not actually "whichever renders later" as if nondeterministic: `NodeRenderer.tsx` always renders `buildSpotlightRevealCss`'s `<style>` tag AFTER `compileNodeStateCss`'s, in a fixed, deterministic sibling order — so `buildSpotlightRevealCss`'s `::after` rule **always** wins over `compileNodeStateCss`'s `after` rule for the same node, every render, not merely "whichever happens to come later." **(I1, final review fix)** `compileNodeStateCss` now also takes optional `responsiveOverrides`/`breakpoint` params (`NodeRenderer.tsx` passes `props.node.responsiveOverrides, props.context.device()`, mirroring the adjacent `buildBackgroundAnimationCss` call) and resolves the effective style via `resolveEffectiveStyle()` before reading `.hover`/`.focus`/`.active`/`.before`/`.after` — previously it read the node's base `style` only, so a hover/focus/active/before/after style authored while the Inspector's preview breakpoint was Tablet/Mobile (which routes the *entire* Style tab into `responsiveOverrides.<bp>.style`) saved successfully but rendered nowhere, on any device.

**`typography.role`** (`TypographyRole` enum: `display|h1|h2|h3|h4|bodyLg|body|small|caption`) resolves via `resolveTypographyRoleCss()` to `var(--type-<role>-*)` CSS var references (`font-size` wrapped in `clamp(min, 5vw, max)` for fluid sizing, plus `font-weight`/`line-height`/`letter-spacing`) — an explicit field still wins over the role default, matching this function's existing "explicit overrides role default" convention. `TextNode.tsx` renders the real matching semantic HTML tag (`<h1>`-`<h4>`, `<p>`) via Solid's `<Dynamic component={tagForRole(role)}>` — **only for the plain-text render branch**; the rich-text (`innerHTML`), video-fill, and count-up branches are unchanged and always render their own fixed wrapper element. **(C1, final review fix — merge blocker)** on that plain-text branch, `<Dynamic>`'s tag is only known at runtime, so Solid's `use:nodeAnimation` directive (which only compiles to a real directive call on a compile-time-known native tag) silently degraded to a dead `setAttribute`, and the Animation Timeline never ran for any plain-text Text node — the most common node type in the app. Fixed by calling the directive's underlying `nodeAnimation(el, accessor)` function directly from a `ref` callback instead of `use:`. **(I4, final review fix)** every `var()` reference now also carries a fallback value (e.g. `var(--type-h1-min, 32px)`), and the function now also returns `fontFamily` (`var(--font-display)` for `display`/`h1`-`h4`, `var(--font-body)` for the rest, wired into `applyNodeStyle.ts`) — previously an undefined `--type-*` var (true for every theme created via the admin UI, which never writes `typography.scale`) made the whole declaration set invalid-at-computed-value-time and silently dropped, and `typography.role` never set a font-family at all despite the theme layer already injecting `--font-display`/`--font-body` and loading their Google Font `<link>`s.

### 4.6 Layout & Grid + typography measure/balance

Built across a 9-task plan (`docs/superpowers/plans/2026-08-29-layout-grid-typography.md`, spec `docs/superpowers/specs/2026-08-29-layout-grid-typography-design.md` — both still present in the repo at these paths, same as §4.5's own plan/spec docs), this is **Phase 2** ("grid/section layout primitives and a real Typography Inspector beyond the role selector") of the wider design-system roadmap in `feedback/UPGRADE-PROMPT.md` — see §4.5's own scope-boundary note for where this sits relative to Phase 1. FE-only; no BE changes were needed (`ThemeEntity.layout` already carried every field this phase consumes — `containerWidths`, `sectionPadding` — from Phase 1).

**Theme token plumbing** — `resolveThemeCssVars.ts` (FE) emits `--section-padding-{desktop,tablet,mobile}-{min,max}` (from `theme.layout.sectionPadding`, a `[min,max]` px tuple per breakpoint) alongside the pre-existing `--container-content`/`--container-wide` vars (Phase 1 already emitted these two; this phase is their first real consumer).

**`containerWidth` (section mode)** — a new `LayoutProps.containerWidth?: 'content' | 'wide' | 'full'` field on a FRAME node's own `layout` (`node.types.ts`). Semantics, implemented in `applyContainerLayout()` (`applyNodeLayout.ts`): the FRAME's own box (`outer`) always spans 100% of its parent's width (full-bleed background) regardless of tree position, and gets a fluid `padding-block: clamp(var(--section-padding-<bp>-min), 8vw, var(--section-padding-<bp>-max))` — **unless** the node already has an explicit `style.spacing.padding.t`/`.b`, which always wins over the token default (same "explicit beats token default" rule the rest of the style pipeline follows). For `'content'`/`'wide'`, an additional `inner` wrapper `<div>` is rendered (`FrameNode.tsx`) around the FRAME's children, centered (`margin-inline: auto`) and constrained to `var(--container-content)`/`var(--container-wide)`; `'full'` skips that wrapper (full-bleed, no max-width, but keeps the section padding). Unset `containerWidth` (the overwhelming majority of existing FRAMEs) renders byte-identical to before this phase — live-verified (see below). **Real DOM shape**: `NodeRenderer.tsx`'s `[data-node-id]` wrapper → FrameNode's own root element (`outer` CSS) → (only when `containerWidth` is `'content'` or `'wide'` — **not** `'full'`, which has no `inner`) the `inner` wrapper div → the FRAME's actual children. **(I1, final whole-branch review fix)** this wrapper is now rendered consistently across **all** of FrameNode's render branches — a shared `FrameChildren` helper is used at every `<NodeChildrenList>` call site in the file (the default `<a>`/`<div>` branches, the carousel branch's active-entry list, and the accordion branch's trigger **and** body) — previously only the default `<a>`/`<div>` branches (2 of 4 render sites) actually consulted `innerContainerStyle()`, so a Frame combining `containerWidth` with the accordion/carousel `behavior` silently lost the full-bleed/centered-content split.
- **Critical bug found and fixed mid-plan (Task 5's review, revert-and-retest verified)**: `applyContainerLayout`'s arrangement CSS (`display`/`flex-direction`/`gap`/`justify-content`/`align-items`/`grid-template-columns`) originally always landed on `outer`, even when an `inner` wrapper exists — since the real children render inside `inner`, not `outer`, this silently dropped all arrangement (e.g. a `containerWidth:'content'` section with a `gap` rendered its children with zero spacing between them). Fixed: arrangement CSS now lands on `inner` when it exists, `outer` only when it doesn't (`containerWidth` unset or `'full'`).
- **Inspector UI**: `NodeContainerLayoutTab.tsx` gained a "Chế độ Section" (`cms.node.containerLayout.containerWidthLabel`) `<Select>` with 4 options (none/content/wide/full — `containerWidthNone/Content/Wide/Full` i18n keys) writing `layout.containerWidth`.

**12-column grid, friendly child API** — `LayoutProps.colSpan?`/`colStart?: number` (1-12, no range validation in the data layer — the Inspector clamps it) on a FRAME's CHILD node's own `layout`, read by `applyChildLayout()` **only when the PARENT's resolved `layout.display === 'grid'`** (`parentDisplay`, threaded FRAME → `NodeChildrenList` → `NodeRenderer` → `applyChildLayout`, mirroring how `parentLayoutMode` already threads through the same call chain). Compiles to a real `grid-column: <colStart ?? 'auto'> / span <colSpan>` — takes priority over the pre-existing raw `gridColumn` string escape hatch when both are set. Varies per breakpoint via the pre-existing Phase-1 `responsiveOverrides` mechanism with zero new plumbing (`resolveEffectiveLayout()`'s desktop-first cascade already covered any `LayoutProps` field, `colSpan`/`colStart` included, the moment the type gained them).
- **Inspector UI**: a new `NodeGridItemTab.tsx` — colSpan/colStart numeric inputs — shown **only** when the selected node's PARENT has `layout.display === 'grid'` (same parent-inspecting-gate pattern `NodeTransformTab.tsx` already established for `layoutMode==='free'` children, byte-for-byte). One disclosed latent edge case (Task 7 review, non-blocking, out of scope): `layoutMode` and `layout.display` are independent fields, so a data shape that sets both a free-layout-triggering condition AND `display:'grid'` could theoretically show both the Transform tab and the Grid Item tab at once — not reachable through the Inspector's own UI today, a data-model quirk only.

**Typography measure + heading balance** — `resolveTypographyRoleCss.ts` (already emitting `font-size`/`-weight`/`line-height`/`letter-spacing`/`font-family` per `TypographyRole` since Phase 1) now also returns:
  - `textWrap: 'balance'` for every heading-shaped role (`display`, `h1`-`h4` — `DISPLAY_ROLES`), so a wrapping heading breaks onto more visually even lines instead of leaving one short orphan word/line.
  - `maxWidth: '65ch'` for body-shaped roles only (`body`, `bodyLg` — `MEASURE_ROLES`) — the fixed value from `feedback/UPGRADE-PROMPT.md`'s own "60-75ch" range, not theme-configurable (YAGNI — no request for per-theme tuning).
  Both are applied in `applyNodeStyle.ts`'s `t.role` block; the `max-width` is skipped whenever the node already has an explicit `style.size.width` set — same "explicit beats role default" precedent Phase 1 established for color/font-family. `TextNode.tsx` already rendered the real semantic tag (`<h1>`-`<h4>`/`<p>`) per role since Phase 1 (`tagForRole`), so no renderer change was needed here — both new CSS properties simply ride the existing per-role `style()` computation.

**Live verification (Task 9)** — real dev servers, a disposable QA admin, and a genuine browser (see the top-level verification report for full detail): a `containerWidth:'content'` FRAME's computed `padding-block` matched the active theme's `sectionPadding` token (`clamp(96px,8vw,144px)` → `115.2px` at a 1440px viewport, `32px` at a 400px mobile viewport, both via the real `useBreakpoint()`/`--section-padding-<bp>-*` var selection, not just `vw` scaling within one token pair) and the inner wrapper's computed `max-width` matched `--container-content` (`1280px`) exactly; a `display:grid` FRAME with two children (`colSpan:7` and `colSpan:5,colStart:8`) produced real computed `grid-column-start`/`-end` tracks (`auto/span 7`, `8/span 5`); switching the Node Builder's Desktop/Tablet/Mobile preview switcher to Mobile changed a `responsiveOverrides.mobile`-scoped `colSpan` (7 → 12) and the section-padding token pair (desktop `128px` → mobile `48px`, at a fixed real browser viewport, proving the breakpoint switcher — not window resize — drives which token pair the canvas reads) live in the DOM, confirmed in both the public site and the admin canvas independently; an `h1`-role node computed `text-wrap: balance` and a `body`-role node computed a finite pixel `max-width` (`703.04px` for 65ch at the theme's default body font); a pre-existing Phase-1-era demo page (`/game`, no `containerWidth` anywhere in its tree) rendered with zero console errors and no structural change.

### 4.8 Image/Media art-direction

Built across a 7-task plan (`docs/superpowers/plans/2026-08-29-image-media-art-direction.md`, spec `docs/superpowers/specs/2026-08-29-image-media-art-direction-design.md`) — **Phase 4** of the wider design-system roadmap in `feedback/UPGRADE-PROMPT.md`, the phase the Phase-completeness table below used to flag as "Not started". `ddd-graphql-fe` only, Tasks 1-6 (Task 7 is this documentation/regression pass, commits `9b824e2..c745e24`). No BE changes this phase (`StyleObject.image` lives entirely inside the FE's own `Mixed`/jsonb `style` column, same as every other style field group). Adds art-direction controls to `ImageNode` — aspect ratio presets, focal-point recentering, duotone/grayscale color treatment, an overlay gradient layer, non-rectangular clip masks, and a scroll-reveal entrance animation — closing the "generic/distorted image" gap `feedback.md` flagged for this phase.

**`StyleObject.image` field group** (`node.types.ts`, optional, meaningful only on `ENodeType.IMAGE` — same convention as `typography`/`background` being meaningful only where relevant): `aspectRatio?: '1:1'|'4:3'|'3:2'|'16:10'|'16:9'|'21:9'`; `focalPoint?: {x,y}` (0-100, percentages → CSS `object-position`); `treatment?: 'none'|'duotone'|'grayscale'`; `duotone?: {from,to}` (same `string|ThemeColorTokenRef` union every other color field uses, resolved through the same `resolveColorValue()` helper); `overlayGradient?: string` (raw CSS gradient, same convention as `background.overlay`); `mask?: 'none'|'circle'|'blob'|'diagonal'`; `revealOnScroll?: boolean`.

**`applyNodeStyle.ts`** — a new `if (effective.image)` branch (after `effects`) emits `aspect-ratio` from the 6-preset map, `object-position` from `focalPoint`, `clip-path` from the 3-preset `mask` map (`circle(50% at 50% 50%)` / an 8-point `polygon(...)` blob / a 4-point diagonal `polygon(...)`), and pushes a `grayscale(1)` base filter for `treatment:'duotone'`/`'grayscale'` into a `filters` array. **Critical shared-filter fix (Task 2):** `filters` used to be declared INSIDE the `effects` block, so `image.treatment`'s grayscale had no way to combine with `effects.blur`/`.grayscale` — one clobbered the other. It's now declared once, above both blocks, and `css.filter = filters.join(' ')` runs after both have had a chance to push into it — an ImageNode with both an Effects-tab blur and an art-direction treatment gets both (`blur(6px) grayscale(1)`), confirmed in a real computed style during Task 7's live verification, not just the unit test.

**`ImageNode.tsx` structural change** — restructured from a bare `<img>` to `<div><img/>{overlay}</div>`. The wrapper carries everything `applyNodeStyle()` returns; the `<img>` itself carries only `object-fit`/`object-position`/`filter` (`IMAGE_ONLY_CSS_KEYS`, hoisted to its own `imageOnlyStyleKeys.ts` module by the final-review fix round below so `compileNodeStateCss.ts` can share it). `object-fit` defaults to `'cover'` when unset — a deliberate, disclosed visual change, not a regression: when no explicit size/aspect-ratio is set the wrapper's height stays `auto` so `object-fit` is a true no-op (byte-identical); but a PRE-EXISTING node with an explicit `size.height` and no explicit `objectFit` used to stretch/distort via the browser's implicit `object-fit:fill` default, and now correctly crops via `cover` — exactly the "generic/distorted image" problem this whole phase exists to fix. `loading="lazy"` added unconditionally. An overlay `<div>` (absolutely positioned, `mix-blend-mode:color` for duotone, `normal` for a plain `overlayGradient`) renders when `treatment:'duotone'` or `overlayGradient` is set; duotone wins if both are somehow set (confirmed correct in code, not just documented, Task 4's review). **Correction (final-review fix I-1):** the `<img>` does NOT unconditionally fill its wrapper with `width/height:100%` as originally shipped — it only does so when the wrapper actually has a defined size to fill (`image.aspectRatio` set, or `style.size.width`/`.height` explicitly set); see below.

**Filter-placement bug — found and fixed live (Task 7):** the brief called for live-verifying duotone "renders correctly over a real image," and a real headless-Chromium render of `treatment:'duotone'` showed a flat black-and-white image with **zero color tint** — the feature was completely broken despite every unit test (Tasks 1-6, all jsdom) passing. Root cause: `filter` was NOT originally in `IMG_ONLY_KEYS`, so `grayscale(1)` landed on the WRAPPER, which also contains the duotone overlay `<div>`. CSS `filter` on a parent applies to the composited rendering of its entire subtree as one unit — so the wrapper's filter grayscaled the img+overlay AFTER the overlay's `mix-blend-mode:color` had already tinted it, stripping the color right back out. Fixed by adding `filter` to `IMG_ONLY_KEYS` and applying it to the `<img>` alone (commit `c745e24`); the overlay now blends its color against an already-desaturated-but-separately-composited image, producing the intended tint. Verified live after the fix: duotone renders genuinely purple-to-orange (and green-to-blue, via the Inspector click-through below) tinted, on both light and dark page backgrounds; the `blur(6px) grayscale(1)` combo and the non-overlay plain-`grayscale` case are visually unaffected (single element, no compositing order to get wrong). No unit test caught this and none was retrofitted to (jsdom cannot composite `mix-blend-mode`) — this class of bug is only reachable by real-browser rendering, consistent with this project's established pattern of live click-through catching what static/jsdom review misses (see §4.7's Task 12, §4.3's Phase 1c, etc.).

**`revealOnScroll`** — a one-time `IntersectionObserver` on the wrapper (not the `<img>`/overlay), transitioning `opacity`/`transform` from `scale(1.05);opacity:0` to `scale(1);opacity:1` over `var(--motion-reveal, 700ms)`, disconnecting itself after the first trigger (verified live: scrolling the revealed node out of view and back does NOT re-fade it). Guarded twice against `prefers-reduced-motion: reduce` — no observer is created for a reduced-motion visitor, so they simply stay in the (now default, see below) revealed state with no scroll interaction required. **Correction (final-review fix I-4): the "SSR trade-off, disclosed, not fixed" claim that used to be here is no longer accurate — it IS fixed.** The `revealed` signal now always starts `true` regardless of `shouldReveal()`; the transition to the pre-reveal HIDDEN state happens only inside `onMount` (client-only — never runs during SSR), immediately before the `IntersectionObserver` is created. So the server-rendered / no-JS HTML always ships the fully-revealed state (`opacity:1`, `scale(1)`, no forced pre-reveal hiding) — confirmed via a real Solid `renderToStringAsync` SSR test (`ImageNode.ssr.test.tsx`, `npm run test:ssr`), not just reasoned about. **Correction (final-review fix I-3):** `revealOnScroll`'s `opacity`/`transform` no longer unconditionally OVERWRITE whatever `effects.opacity`/`transform.*` already computed for the node — they now COMPOSE (opacity multiplies the reveal's 0/1 factor into the base opacity; the reveal's `scale(...)` is appended to the end of any existing `transform` string), so a node can have both an independent rotation/opacity AND `revealOnScroll` without one silently destroying the other.

**Inspector UI** — `NodeStyleTab.tsx` gained an "Ảnh" (Image) `InspectorSection`, gated on `props.isImage` (`selected()?.type === ENodeType.IMAGE`, wired in `NodeBuilder.page.tsx`): a `Select` for `aspectRatio`, two `InputNumber`s for `focalPoint.x`/`.y`, a `Select` for `treatment`, two `ColorTokenOrCustom` pickers for `duotone.from`/`.to` (shown only when `treatment==='duotone'`), a raw-text input for `overlayGradient`, a `Select` for `mask`, and a `Checkbox` for `revealOnScroll` — every `onChange` spreads the full existing `style().image` object before writing (full-`StyleObject`-spread write-through, confirmed correct in code, Task 6's review).

**Final-review fix round (post-Task-7)** — a whole-branch final review of this 7-task plan found 2 Critical and 4 Important issues in the Task-7-shipped state, all now fixed:

- **C-1 (Critical) — hover-state `filter` became inert.** Task 7's fix (commit `c745e24`) moved `filter` off the wrapper onto the `<img>` alone (correctly fixing the duotone-erasure bug), but `compileNodeStateCss.ts` still only ever compiled hover/focus/active CSS against the WRAPPER selector (`[data-node-id="ID"] > *`) — so a `hover.effects.grayscale` override (a real, pre-existing, zero-new-code UI pattern per `NodeStyleTab.tsx`'s base+hover grayscale sliders) became a silent no-op: the wrapper doesn't carry `filter` anymore, and the `<img>`'s own inline `filter` was untouched by the compiled rule. Two fix options were evaluated and EMPIRICALLY tested in a real Chromium browser (not just reasoned about): (A) also emit a second compiled-CSS selector targeting the `<img>` directly; (B) revert `filter` to the wrapper and shield the overlay from it via `isolation:isolate`. A real-browser pixel test proved Option B does NOT work — `isolation` on the overlay child does NOT shield it from an ancestor's `filter` (a wrapper-level `filter:grayscale(1)` still fully desaturated an `isolation:isolate` overlay's blended output down to flat gray, `rgb(114,114,114)`, identical to the no-isolation control) — `filter` on a parent processes that parent's ENTIRE composited subtree, a stage `isolation` (a blend-mode-only stacking-context scope) cannot opt out of. **Option A was implemented**: `compileNodeStateCss.ts`'s new `stateSelectors()` emits an additional `[data-node-id="ID"] > * > img` selector (only for the subset of compiled properties in the new shared `imageOnlyStyleKeys.ts`'s `IMAGE_ONLY_CSS_KEYS` — `filter`/`object-fit`/`object-position` — never the full override, to avoid compounding properties like `opacity` doubling across wrapper+img). Verified live: a base-gray/hover-color node went from "stays gray on hover" (bug) to "restores full color, `rgb(51,170,51)`, on hover" (fixed), while the duotone-tint-survives-an-unrelated-hover case (`rgb(184,112,135)` before AND during hover) confirms this doesn't reintroduce the original Task-7 bug. New tests: `compileNodeStateCss.test.ts`'s `C-1: filter-bearing overrides also target a descendant <img>` suite.
- **C-2 (Critical) — `ImageNode.tsx` read `style.image` from the BASE style only, ignoring `responsiveOverrides`.** `overlayBackground()`/`hasOverlay()`/`overlayMixBlend()`/`shouldReveal()` all read `props.node.style?.image` directly, bypassing `responsiveOverrides` entirely — while `fullStyle()` DID correctly merge them (via `applyNodeStyle`'s 3-arg overload). A `treatment:'duotone'` set only inside `responsiveOverrides.mobile.style.image` therefore got its `filter:grayscale(1)` correctly applied but NO overlay div at all when rendering at the `'mobile'` breakpoint — a flat grayscale image with zero color tint on real phones. Fixed (the same bug class `compileNodeStateCss.ts` and `buildBackgroundAnimationCss` were each fixed for before) by computing one `effectiveStyle()` via `resolveEffectiveStyle()` once per render and reading `.image` from it everywhere. New tests in `ImageNode.test.tsx`'s `(C-2)` cases, plus a real-Chromium visual/pixel check (the buggy path renders the raw unblended photo, `rgb(51,170,51)`; the fixed path renders the correctly tinted overlay, `rgb(184,112,135)`, matching the same tint elsewhere on the page).
- **I-1 (Important) — unconditional `width:100%;height:100%` on the `<img>` stretched unsized images.** Now only applied when the wrapper actually has a defined size to fill (`image.aspectRatio` set, or `style.size.width`/`.height` explicitly set) — a fresh Image node or a small icon with neither now renders at its natural intrinsic size again, matching pre-plan behavior, instead of stretching to full container width.
- **I-2 (Important) — `border-radius` on the wrapper didn't clip the `<img>`.** `border-radius` only clips an element's OWN painting, not descendant content, unless `overflow` isn't `visible`. `wrapperStyle()` now defaults `overflow:'hidden'` whenever a radius is present and the admin hasn't explicitly chosen their own `overflow` value (an explicit choice is always respected).
- **I-3 (Important) — `revealOnScroll` clobbered independently-set `transform`/`opacity`.** Now COMPOSES: the reveal's `scale(...)` is appended to the end of any existing `transform` string; the reveal's 0/1 factor MULTIPLIES into any existing base `opacity` rather than replacing it.
- **I-4 (Important) — `revealOnScroll` didn't actually deliver its own spec's SSR-safe guarantee.** The `revealed` signal now always starts `true`; the pre-reveal hidden state is entered only inside `onMount` (client-only). Confirmed via a real Solid `renderToStringAsync` SSR test (`ImageNode.ssr.test.tsx`) — the server-rendered HTML now genuinely ships `opacity:1; transform:scale(1)`, not the pre-reveal hidden state.

### 4.11 Section/Pattern Library + Art-Direction Starter Kits (Phase 6)

Built across an 18-task plan (`docs/superpowers/plans/2026-08-31-section-pattern-library.md`, spec `docs/superpowers/specs/2026-08-31-section-pattern-library-design.md`), this is **Phase 6** ("Section/Pattern library + Art-direction starter kits", §4.H of `feedback/UPGRADE-PROMPT.md`) of the wider design-system roadmap — see §4.5's own scope-boundary note for where this sits relative to Phases 1-5. **`ComponentDefinition.category` is the entire BE data-model change this phase makes** (Task 1, `component.entity.ts`) — a nullable, additive `string` column, same "plain varchar, never a real TS enum" convention `ENodeType`/`EPageType` already follow. It is **never writable through GraphQL**: `CreateComponentFromSelectionInput` (`component.dto.ts`) has exactly 5 fields (`key`/`label`/`icon`/`pageId`/`nodeIds`) and deliberately no `category`, confirmed by reading the class directly — so an admin's ordinary "Save as Component" action can never accidentally produce a curated-looking row. The only writer is `ComponentService.createSectionDefinition` (validates `category` via `isSectionCategory()`, then goes through the same `assertKeyAvailable` uniqueness guard `create()` normally skips), called only by the in-process seed runner (`scripts/seed-section-library.ts`) — exactly mirroring how `scripts/seed-default-theme.ts` calls `ThemeService.createTheme` directly rather than through a mutation. `category` set ⇒ `NodePalette.tsx`'s new "Sections" tab; unset ⇒ the pre-existing "Components" tab, unchanged (regression-checked in Task 1's own review). A Section reuses `insertComponentInstance`/`publishComponent`/`detachComponentInstance` **verbatim** — no new instance-tracking table, no new publish mechanism, no new override model; a placed Section is, underneath, just a Component instance whose definition happens to have `category` set.

**`SECTION_CATEGORIES`** — 12 members (`hero`, `feature-grid`, `editorial`, `stats`, `logo-wall`, `testimonial`, `menu-list`, `gallery`, `cta`, `pricing`, `faq`, `contact-booking`), hand-mirrored BE (`src/modules/component/domain/constants/section.constants.ts`) ↔ FE (`src/modules/cms/node/section.constants.ts`) byte-for-byte, with no shared package or codegen between the repos — the same convention already documented for `EErrorCode`, §6.3.

**The authoring model** (Task 4, the foundation all 11 later category tasks build on) — `SectionVariantSpec`/`SectionNodeSpec`/`SectionPropSpec` (`scripts/sectionLibrary/sectionSpec.types.ts`) are pure, side-effect-free data describing a Section's definition subtree, plus `token()`/`scrollReveal()` helper functions. One shared `seedSectionVariant()` runner (idempotent — `findByKey`-first, skips a row that already exists) materialises a spec into a real definition Page + Node subtree. `scripts/sectionLibrary/index.ts` is the single `SECTION_LIBRARY` registry — each category task appends exactly one import line + one spread entry, nothing else about the runner or the test suite changes as the library grows. The shared invariants suite (`test/scripts/sectionLibrary.invariants.test.ts`) mechanically enforces, over every entry in `SECTION_LIBRARY` at once: non-emptiness; `section-<category>-<slug>` key format + uniqueness; real-`SECTION_CATEGORIES`-membership + a label/icon on every variant; unique refs and exactly one root per subtree; **no literal hex/`rgb()` color anywhere**; **every `TEXT` node sets `style.typography.role`**; **only allowed `ENodeType` primitives** (no invented node type); every `propSchema` entry targets a real ref with a unique `propKey`; and **no two variants share a placeholder image URL** (spec §3.5's seed-data-uniqueness rule) — plus a per-variant `it.each` seed-and-clone smoke test and a whole-library idempotent-reseed test.

**The 23 variants across 12 categories**: hero 5 (`cinematic-fullbleed`/`split-editorial`/`centered-minimal`/`photography-led`/`typographic`), feature-grid 2 (`icon-cards-3col`/`numbered-rail-4col`), editorial 2 (`single-column-measure`/`two-column-lede`), stats 2 (`typographic-row`/`repeat-cards`), logo-wall 1 (`grayscale-wrap`), testimonial 3 (`story`/`quote-large`/`carousel`), menu-list 1 (`dotted-leader`), gallery 1 (`masonry-mixed`), cta 3 (`band`/`split`/`minimal`), pricing 1 (`tier-grid`), faq 1 (`accordion-list`), contact-booking 1 (`form-panel`) — 5+2+2+2+1+3+1+1+3+1+1+1 = 23, all 12 categories covered, arithmetic independently re-verified during this task. **`ArtDirectionKitEntity`** (Task 2, table `art_direction_kit`) — a thin manifest, not a content-authoring surface: 6 fields (`name`, `industry`, `themeId`, `headerPresetId`, `footerPresetId`, `templates: KitTemplate[]` as untyped jsonb). `KitTemplate` = `{ templateKey, label, sectionComponentIds: string[] }` — an ordered list of curated-Section `ComponentDefinition` ids, one instance inserted per entry, in order. **`createPageFromKit`** (Task 3) — pure orchestration over `PageService.createPage()` followed by a loop of `ComponentService.insertComponentInstance()` calls, one per `sectionComponentIds` entry in order. If a Section insertion fails partway through the loop, the newly-created Page is compensating-hard-deleted so the caller never ends up with a half-seeded page. `createPageFromKit` is STAFF-writable, not ADMIN-only, because — unlike the Theme/Preset/Kit entities it reads from — it only ever creates a *page*, the same authorization level `createPage` itself already requires. The resulting Page is completely ordinary: nothing about it is "kit-locked", and `templateKey` is written onto the Page purely as provenance/bookkeeping — no runtime resolver or renderer anywhere reads it back.

- **`Select`'s `clearable` prop never reached `NativeSelect`** (`src/core/components/control/Select.tsx`, commit `990a63c`). `<Select native clearable>` — Phase 6's `KitStarterFields.tsx` kit picker is the only real caller of `native` in the whole codebase, so the gap was never exercised before — computed a `clearable()` helper gated on `value() !== ''` for its own wrapper's "×" button, but never forwarded the caller's raw `clearable` prop into `<NativeSelect>`, whose blank `<option value="">` only renders when `props.clearable` is truthy. A freshly-uploaded image's bare-UUID `src` then resolved as a *relative* URL against the current admin route (`/admin/cms/node-builder?pageId=...` → `/admin/cms/{id}`) — which 200s with the SPA's own `index.html` (`content-type: text/html`), not an image, so every image ever uploaded through the Node Builder rendered broken, silently. This is the exact bug class `valueMode` was already built to fix elsewhere; the Node Builder's own field renderer had simply never been updated to opt in. Fixed with one prop (`valueMode="url"`), covered by a new `FieldRenderer.test.tsx` (stubs `compressImageFile` — jsdom has no real canvas, so `InputImage`'s compressorjs step never resolves in-test otherwise), re-verified live via a real S3-backed upload (`img.naturalWidth: 1920` after the fix, vs. `0`/`text/html` before).

**Minor, non-blocking friction disclosed, not fixed:** clicking a Nút bấm/link node directly on the canvas fires its `href` (adds `#anchor` to the browser URL) instead of only selecting it for Inspector editing — worked around by selecting via the Layers tree instead; still fully editable, just an extra click. ## 6. Cross-cutting mechanisms

### 6.1 Permission/authorization, end to end

1. **BE, coarse gate**: `@GQLAuthorized([...ERole|ERoleScrope])` or `@GQLPublic()` on the resolver method → checked first in `createResolverHandler` (`graphQLSchema.loader.ts`) via `RBACService.authorizeRoles`.
2. **BE, fine gate**: `@GQLPermission({ permission: EPermission.X, ... })` → `applyGQLPermission()` resolves an `AccountPermissionEntity` row's `ScopeRule` into `ALLOW`/`DENY`/`FILTER`; owners/agency accounts bypass via role check before any DB lookup.
3. **FE gating**: no generic client-side permission-gating layer was found beyond feature-specific `<Show when={...}>` checks and role-driven sidebar menu filtering (`SidebarMenus.ts`) — permission enforcement is fundamentally BE-driven; the FE trusts GraphQL errors (`PERMISSION_DENIED`, etc.) for anything it doesn't proactively hide.

### 6.2 Feature flags — full current list

| Flag | Side | Env var | Default | Purpose |
|---|---|---|---|---|
| GraphQL introspection/landing page | BE | `ENABLE_GRAPHQL_INTROSPECTION` | `false` (always on outside prod regardless) | Controls introspection in production only |
| DB schema sync | BE | `DB_SYNCHRONIZE` | effectively "on in dev, off in prod" | Lets TypeORM `synchronize()` run; also usable for a fresh `INSTANCE_ROLE=NODE` bootstrap |
| Skip migrations | BE | `DB_SKIP_MIGRATIONS` | `false`, and only honored when `NODE_ENV=test` | Test-only escape hatch |
| Multi-instance role | BE | `INSTANCE_ROLE` | `CENTRAL` | `NODE` filters resolver/controller files via an (empty, no-op) module denylist |
| DB TLS | BE | `DB_SSL` | `false` | Enables `{rejectUnauthorized:false}` TLS to Postgres |
| Redis cache | BE | `REDIS_HOST` presence | unset = no-op cache | Gates `/health/ready` Redis check and real cache backing |

`PublicConfig` (FE, `src/env.config.ts`) also carries non-boolean runtime config (`APP_NAME`, `BACKEND_URL`, `ENVIRONMENT`, `PORT`, `HOSTNAME_DEFAULT`, `HOSTNAME_ADMIN`, `SEO_PUBLIC_PATH`) — not feature toggles.

### 6.3 i18n key namespaces

FE UI i18n: `common`, `locale`, plus one namespace per module co-located with its feature (`adminVi`, `agencyVi`, `authVi`, `cmsVi`, `codeConfigVi`, `merchantVi`, `tenantAuthOrgVi`, `tenantStaffVi`, `unitVi`, `layoutsSharedVi`), merged into `dictionaries/{vi,en}.ts`. BE error-message i18n is a **separate** mechanism: `EErrorCode` enum (namespaced `<DOMAIN>_<REASON>`, e.g. `AUTH_INVALID_CREDENTIALS`, `PERMISSION_DENIED`, `TENANT_CODE_DUPLICATE`) translated server-side per the request's `x-locale` header (default `vi`, fallback `Accept-Language`); the FE never re-translates, only branches on `error.extensions.code` (`src/shared/errors/errorActions.ts`). The two enums (BE `EErrorCode`, FE's consumption of `.code`) are manually mirrored — no shared package or codegen keeps them in sync.

### 6.4 GraphQL codegen — confirmed broken

FE `package.json` defines `"codegen": "graphql-codegen"` (with `@graphql-codegen/cli`/`typescript` installed as devDependencies), but **no config file exists anywhere in the repo** (checked for `codegen.ts/.yml/.yaml/.json`, `graphql.config.*`, `.graphqlrc*` at root and in every subdirectory). Running `npx graphql-codegen` reproduces exactly the previously-reported failure: `Error: Unable to find Codegen config file!`. This script is vestigial/dead. **The actually-used, working pipeline is different**: `npm run gengraph` → `scripts/generate-graph.mjs`, which introspects a running BE at `BACKEND_URL`, rewrites `src/shared/generated/schema.graphql`, then shells out to the real `typed-graphql-builder` CLI (not `@graphql-codegen`) to regenerate `typed-graphql.ts`, followed by a post-generation patch step (scalar overrides from `src/core/config/scalars.txt`, `@ts-nocheck`, `fn()` overload injection). `npm run genservicegraph` / `npm run gen:service` (plop) scaffold new service files. To regenerate against a real schema: run `ddd-graphql-be` locally, point `.env`'s `BACKEND_URL` at it, run `npm run gengraph`.

- **Content localization has a known v1 limitation**: `MenuItem.targetType=PAGE` hardcodes one `pageId` and does not follow the current viewer's locale — explicitly flagged in code/plan comments as deferred, not a bug.
- **`:focus-visible` parent-scope styling trades away keyboard-only semantics** — `compileNodeStateCss.ts`'s parent-scope focus rule uses `:focus-within` (the only CSS selector that both propagates to ancestors and can express "a descendant is focused"), so a parent-scope focus override also fires on a plain mouse click, not just keyboard focus. Self-scope focus is unaffected (keyboard-only, verified live). An inherent CSS limitation, disclosed as a deliberate trade-off, not an oversight.
- **`compileNodeStateCss.ts`'s `::before`/`::after` support can collide with `applySpotlightRevealStyle.ts`** — a node with both `props.spotlightReveal===true` and a `style.after` value would get two competing `::after` declarations on the same selector shape. **(M4, final review — corrected)** not "whichever renders later" as if nondeterministic: `NodeRenderer.tsx` always renders `buildSpotlightRevealCss`'s `<style>` tag AFTER `compileNodeStateCss`'s in a fixed sibling order, so `buildSpotlightRevealCss`'s `::after` rule **always**, deterministically, wins for the same node. Pre-existing architectural seam between two independent CSS-generating modules, not reconciled by this plan; no live node currently sets both.
- **`isThemeColorTokenRef`'s runtime check doesn't validate the `tokenRef` key** (M3, final review) — `theme.types.ts`'s `isThemeColorTokenRef` only checks `typeof value.tokenRef === 'string'`, never that it's actually one of `ThemeColorSet`'s 15 real keys (`background`/`surface`/.../`danger`). A typo'd `tokenRef` (e.g. `{ tokenRef: 'primry' }`) passes the guard, then `resolveColorValue()` happily emits `var(--color-primry)` — an undefined custom property that resolves to nothing, so the field silently renders no color instead of failing visibly at save time or render time. Worth a future validation pass (either at the guard itself, or Zod/schema validation on the mutation input); not fixed as part of this round.
- **Chrome (`HeaderPreset`/`FooterPreset`) theme-token conversion is done** (Phase 3 of the wider design-system roadmap, see §4.7) — this bullet used to read "not theme-token-aware... not started"; `SiteHeader.tsx`/`SiteFooter.tsx` are now fully theme-token-aware, zero hardcoded colors (see §4.7's own correction note on how the last hardcoded value — a `rgba()` stroke — was found and fixed). Real gaps found during Phase 3 and still open: **CTA has no mobile-panel counterpart** (`hidden md:inline-flex`, faithful to the design brief's own snippet) — a visitor on a narrow viewport never sees the CTA at all, a real product gap. `HeaderPresetEntity.megaMenu` is `@Column({default:false})` without `nullable:true` — harmless (Postgres backfills existing rows to `false`, matches `isDefault`/`isActive` precedent) but contradicts the letter of the plan's own "every new column nullable" constraint. `SiteHeader.tsx`'s hex→token color mapping collapses 3 visually-distinct legacy grays (`#8a8a8a`/`#6f6f6f`/`#c9c9c9`) onto the single `foreground-muted` token — a reduced-differentiation side effect of the plan's own mapping table, not an implementer choice, worth a design-token-owner look if unintended.
  - **Final whole-branch review fixes (I1-I4/M5/M7)**: the footer outline-text `rgba()` stroke (I1, see above); `SiteHeader.tsx`'s 3 `var(--motion-hover)`/`var(--motion-ease-standard)` sites had no fallback value, so the declaration silently dropped for every admin-created theme (Theme Manager never exposes a `motion.easing` form field) — the exact bug class already fixed once for typography vars, recurring here because motion vars were never given the same treatment; now `var(--motion-hover, 300ms)`/`var(--motion-ease-standard, cubic-bezier(.4,0,.2,1))` (Tailwind's own pre-token-conversion values, byte-behavior-preserving). `layoutVariant:'split'` previously had zero unit-test coverage AND a real rendering bug: its 3 in-flow flex items (logo/CTA/translations, nav pulled out via `absolute`) put the CTA dead-center under `justify-between`, on top of the absolutely-centered nav — fixed by grouping CTA/translations/mobile-button into one trailing wrapper div (mirrors `'centered'`'s existing right-hand-group pattern), verified byte-identical for `'logo-left'` via the pre-existing "defaults to logo-left" test, and now has real test coverage for the first time. The CTA `<Show when={props.cta}>` guard was bare truthiness — since the admin form exposes `cta.label`/`href`/`variant` as 3 independent optional fields, clearing label/href back to `''` left a truthy-but-empty `cta` object that rendered a blank pill button with no way to ever remove it; guard is now `props.cta?.label && props.cta?.href`. Also: the header's conditional `' relative'` class (`layoutVariant==='split'`) was dead code (`position: sticky` already establishes the containing block `absolute`-positioned `<nav>` needs) and was removed; `onScroll()` now runs once inside `onMount` before the listener registers, so a page loaded already-scrolled (deep-link/scroll-restoration) starts with the correct solid/transparent header state instead of always assuming scroll position 0.
  - **Post-re-review correction (N1/N2/N3)**: two claims in the bullet immediately above turned out to be wrong, and were themselves regressions introduced by that same fix pass. (1) The `layoutVariant:'split'` trailing-wrapper fix was applied to the SHARED fallback branch used by both `'split'` AND `'logo-left'` (the default), not gated to `'split'` only — so it was **not** actually byte-identical for `'logo-left'` as claimed: a header with no CTA/translations went from the mobile-menu button being a flat flex sibling to being nested one level deeper inside an always-present wrapper `<div>`, changing `justify-between`'s real-browser distribution (2 effective flex items became 3) for every site without i18n and without a CTA — the single most common configuration. Fixed by gating the wrapper to `layoutVariant() === 'split'` only; `'logo-left'` again renders `ctaEl()`/`translationsEl()`/`mobileButtonEl()` as flat siblings via a Solid `<>` Fragment (no wrapper element). (2) Calling the full `onScroll()` once inside `onMount` also called `setHidden(current > lastScroll && current > 200)` with `lastScroll` still at its `0` initializer — so any page loaded already scrolled past 200px started with the header hidden (`translateY(-100%)`), for every `bgVariant`, not just `'transparent-overlay'`. Fixed by seeding `lastScroll = window.scrollY` and calling `setOverlaySolid(...)` directly in `onMount`, without ever touching `hidden` at mount time. (3) The `300ms` fallback claim for "all 3 sites" was also wrong — see the corrected §4.7 Motion tokens paragraph above (N3): only the header's own transition is `300ms`; both dropdowns are `150ms`. All three were caught in a subsequent re-review of this same commit, not by its own test suite, which passed throughout — new tests were added that fail against the pre-fix code and pass against the fix (revert-and-retest verified for N1/N2).
  - **BE test-suite correction**: `ddd-graphql-be`'s `npm test` reports `Test Suites: 1 failed, 40 passed` (433/433 individual tests still pass) — `scripts/__tests__/migrateGroup2DataSourceToRepeat.test.ts` fails to even load (`TS2307: Cannot find module '../migrateGroup2DataSourceToRepeat'`), a pre-existing issue from an unrelated prior commit that deleted the module it imports. Confirmed unrelated to the Chrome plan or this final-review fix pass. Doesn't gate CI in practice since the individual-test pass count (433/433) is what's actually reported/relied on elsewhere, but the progress ledger's Task 12 entry ("Full regression clean both repos") overclaimed — this suite was already failing to load at that point too, just not caught.
  - **4 additional disclosed gaps found in final whole-branch review, not fixed (out of scope for a bug-fix pass)**: (a) `bgVariant:'transparent-overlay'` has no legibility treatment for foreground text over imagery — the spec called for a text-shadow or alternate token when overlaying a hero image, only plain foreground color is implemented; (b) the mega-menu's `min-w-[480px]` dropdown has no right-edge/overflow handling at narrower `md`-breakpoint widths, nor in `'centered'`/`'split'` layouts where the anchor point differs from `'logo-left'`; (c) `layoutVariant:'centered'`'s right-hand grid column (nav+CTA+translations) has no width ceiling — a long nav combined with a CTA can overflow its 1/3-width grid track; (d) Task 10's admin-form CTA fields were verified via direct GraphQL mutations only, never the actual Select/Input DOM interaction — this is exactly the untested surface that let I4 (the empty-CTA bug) reach a final whole-branch review instead of being caught earlier, worth prioritizing over other coverage gaps for that reason specifically.
- **Theme dark mode (`ThemeColors.dark`) is data-capable but has no activation path** — no `prefers-color-scheme` media-query wiring and no admin UI toggle anywhere; `resolveThemeCssVars()`/the admin canvas injection are both hardcoded to `'light'` mode.
- **FE SSR-layer GraphQL cache staleness affects theme (and header/footer/content) changes** — `core/api/graphql.ts`'s server-side urql client is a process-lifetime singleton on `requestPolicy: 'cache-first'`, reset only by mutations made through that same server-side client instance; admin-panel mutations (browser-side client) never trigger that reset, so a long-running dev/prod Node SSR process can keep serving a stale cached page render until it restarts. Pre-existing behavior inherited from the original Tasks 1-9 SSR pipeline, not introduced by the theme layer, but newly encountered/documented repeatedly during this plan's live verification passes (Tasks 12, 18) — and reproduced a third time, independently, by the Chrome plan's own Task 12 (§4.7) via a per-Page theme switch: a direct BE GraphQL query confirmed the DB write and server-side resolution were both correct immediately, but the FE kept rendering the old theme's colors until its dev-server process was restarted. Same root cause each time, now confirmed across two different plans' verification passes.
- **`typography.scale` (the 9-role fluid-sizing matrix) has no admin editing UI** — set via the seed script or a direct mutation only; the Theme Manager's create/edit form deliberately does not expose it (disclosed v1 scope cut, not an oversight). **(I2, final review fix — partially closed)** the risk this used to carry (an admin-created theme silently shipping with NO scale at all, making `typography.role` completely inert) is now closed on both sides: `ThemeService.createTheme` (BE) backfills `DEFAULT_TYPOGRAPHY_SCALE` whenever the input omits one, and `resolveTypographyRoleCss.ts` (FE) now carries a defensive per-role `var(..., fallback)` regardless. The remaining gap is genuinely UI-only now — an admin still cannot fine-tune the 9-role matrix without a direct mutation.
- No further code fix, only a documentation correction: `NodeStyleTab.tsx` never grew an authoring UI for `style.focus`/`.active`/`.before`/`.after`/`reducedMotionOverride` — only `style.hover` has one (predates this plan). All five are data-model-and-compiler-complete (`compileNodeStateCss.ts` fully supports them) but reachable only via a direct GraphQL mutation. Never in this plan's 19-task scope (Task 16's own brief covers only the role selector + color token picker) — a real, disclosed gap for a future task (I3, final review).
- **`FlowLayoutProps`'s other item-level fields (`order`/`grow`/`shrink`/`basis`/`alignSelf`) have no Inspector UI** — the Layout & Grid plan (§4.6, Phase 2) only built a control for `colSpan`/`colStart` (`NodeGridItemTab.tsx`); `applyChildLayout()` has fully supported `order`/`grow`/`shrink`/`basis`/`alignSelf` since before this plan (they compile to real `order`/`flex-grow`/`flex-shrink`/`flex-basis`/`align-self` CSS), but none of the five has ever had an authoring control anywhere — reachable only via a direct GraphQL mutation. Confirmed true as of this plan's writing (2026-08-29), not a regression.
- **`layoutMode` and `layout.display` are independent fields** — a node whose parent triggers `NodeTransformTab.tsx`'s free-layout gate (`layoutMode==='free'`) AND whose `layout.display==='grid'` is somehow also set could theoretically show both the Transform tab and the new Grid Item tab (§4.6) at once. Not reachable through the Inspector's own UI today (nothing in the Inspector lets an admin set `layout.display` on a free-layout child) — a data-model quirk noted during Task 7's review, not a live bug.
- **No dedicated test for the `containerWidth` Select control** — `NodeContainerLayoutTab.tsx` gained a "Chế độ Section" (`containerWidth`) `<Select>` in Phase 2 (§4.6), but `NodeContainerLayoutTab.test.tsx` (which this codebase's own established convention tests every comparable prior Select addition in this file) has zero test coverage for it.
- **Stale file-header doc comment in `NodeContainerLayoutTab.tsx`** — its header comment still lists only the pre-Phase-2 fields it exposes (`display`/`gridTemplate`/`direction`/`wrap`) and doesn't mention the new `containerWidth` field the same file now also renders.
- **`size.maxW` is not covered by the typography-role "explicit wins" guard** — in `applyNodeStyle.ts`, an explicit `style.size.maxW` (without `size.width`) sets `css['max-width']` early on, but the LATER typography-role block only checks `effective.size?.width === undefined` before applying the role's `65ch` measure default — so if an admin ever sets `size.maxW` without `size.width` on a `body`/`bodyLg`-role node, the role's default SILENTLY OVERWRITES the admin's explicit value, the opposite of the "explicit beats token default" rule used everywhere else in this pipeline. Currently NOT reachable in practice (`NodeStyleTab.tsx` has no UI control for `size.maxW` at all today) so this is a latent type-level gap, not a live bug — but if `maxW` ever gains a UI control, the guard should check both `width` and `maxW` before applying the role default.
- **`cms.node.image.aspectRatioNone` (both `vi`/`en` dictionaries) is a dead i18n key** — Image art-direction's (§4.8) aspect-ratio `<Select>` in `NodeStyleTab.tsx` relies on the control's own `clearable` prop for the "unset" state rather than an explicit `'none'`/empty option in its `options` list, so this translated label ("Tự nhiên"/"Natural") is defined but never referenced by any JSX. Found during Task 7's docs pass, not fixed (cosmetic, zero functional effect).
- **`ImageNode`'s `object-fit:cover` default is NOT byte-identical for every pre-existing node** (§4.8, Task 3's own disclosure, empirically confirmed live in Task 7) — only true no-op when no explicit size/aspect-ratio was already set (wrapper height stays `auto`). A pre-existing node with an explicit `size.height` and no explicit `objectFit` visibly changes from stretched (the browser's implicit `fill` default) to cropped (`cover`) — deliberate and disclosed, the exact fix this phase exists for, but worth remembering if a future regression report describes "images look different" on an old page that has this exact shape (found live on `/thu-cung`'s pet-photo cards, 6 real nodes).
- ~~`revealOnScroll` (§4.8) has no server-rendered fallback~~ — **fixed** by the final-review fix round (I-4, see §4.8): the `revealed` signal now always starts `true` and only enters the pre-reveal hidden state inside client-only `onMount`, so a no-JS/slow-JS visitor sees the fully-revealed image, not a permanently-invisible one. Confirmed via a real Solid SSR test (`ImageNode.ssr.test.tsx`), not just reasoned about.
- **`compileNodeStateCss.ts`'s img-targeting selector (`> * > img`) could in principle also match a raw `<img>` tag inside `CustomCodeNode`'s admin-authored HTML** (re-review, NEW-4) — only when `isolationMode:'direct'` (the mode that renders straight into the surrounding DOM, not `'shadow'`, which the selector's plain descendant/child combinators cannot cross at all). A low-probability, low-impact edge case: an admin would have to hand-author a `<img>` directly inside a Custom-Code node placed as that node's own hover/focus/active-styled root's direct child, AND that same Custom-Code node's `id` would have to carry a `hover`/`focus`/`active` override touching `object-fit`/`object-position`/`filter` for anything to reach it at all — and even then, those 3 properties are harmless on an unrelated raw `<img>`. Disclosed rather than fixed, since excluding it would add cross-node-type coupling (the CSS compiler would need to know about `CustomCodeNode`'s `isolationMode` prop) for a case unlikely to matter in practice.
